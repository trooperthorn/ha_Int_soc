# Design

Architecture and rationale for HA SOC, organized by subsystem. Wire facts live in `protocol.md`, configuration consequences in `operations.md`, trust boundaries in `security.md`, and dated choices in `decisions.md`. Work item and decision numbers in parentheses refer to `HA-SOC-Security-Work-Plan.md`.

## Module boundaries

Each feature manager is independently testable and knows nothing about the others except through the plain data it reads from `HaSocData` (store.py). The convention shows up in several places: `audit.py` duplicates the refresh-token type constants rather than importing them from `users.py`; `detections.py`, `risk.py`, and `probe.py` import `AuditLog` and `UsersManager` under `TYPE_CHECKING` only, so each stays importable before its peers exist; `store.py` uses literal rule-id strings because `detections.py` imports `store.py`; and `websocket_api._runtime` and `firewall._async_runtime_audit` import `get_runtime_data` locally to avoid a circular import with `__init__.py` at module load. `HaSocConfigEntry` is a plain generic alias rather than a PEP 695 `type` statement so the package stays importable on Python 3.11, not only 3.12 and later.

`const.py` is kept deliberately small: only values that cross module boundaries live there. Module-local constants (risk weights, regex patterns, WS command strings, `DEFAULT_EVIDENCE_RETENTION_DAYS`, `THRESHOLD_SPECS`) live next to the code that uses them. `SIGNAL_UPDATE` is the dispatcher signal that pushes live updates to the panel and triggers the sensor and binary_sensor coordinators, with a topic appended (for example `f"{SIGNAL_UPDATE}_users"`); `EVENT_ALERT` is the custom bus event (`ha_soc_alert`) fired for user-built automations. The shared vocabularies are `LEVEL_ENFORCED`, `LEVEL_COSMETIC`, and `LEVEL_BEST_EFFORT` (shown verbatim in the frontend), `SEVERITY_*` (vulns, misconfig, detections, scanner), `STATUS_*` (finding lifecycle for vulns, misconfig, scanner), and `DETECTION_*` (detection lifecycle).

In `async_setup_entry`, the private secret store is loaded before anything else can want a credential, legacy plaintext copies are drained into it exactly once, and a first analysis pass, config check, and (when enabled) scanner sweep are kicked off shortly after startup rather than after a full interval, so the dashboard is not empty on a fresh install. `async_register_probe_service` is handed the audit log (so a rejected Probe callback is recorded as `probe_auth_rejected`) and the secret store (the pairing secret is pinned and verified there); on non-Supervisor installs it registers nothing. In `_async_vuln_scan`, the tracker fetches the NVD API key from the secret store right before each request (SEC-3); nothing is passed from `__init__.py`.

## Audit chain

External sources: `external_audit.py` lets another tool on the host push its own
hash-chained records (`ha_soc.ingest_audit`); each accepted record becomes an
`external_audit` entry in this chain, and per-source heads in the store make a
break, gap, or rewrite in the source's history detectable here. The first source
is the Elk Programmer app; its session claims also arrive as bus events from the
`elkm1` integration and are recorded as `programming_session`. The contract is in
`protocol.md`; the trust reasoning is in `security.md`.

The audit module (`AuditLog`) is the closest thing HA SOC has to a security camera pointed at Home Assistant's own auth, service, and registry surface. It is intentionally narrow: it listens only to bus events, one dispatcher signal, and log records core already emits, and never to `state_changed` or a `MATCH_ALL` listener. It states honestly what is captured directly, what is inferred, and what is structurally impossible from inside an integration, because overclaiming in a security product is worse than not having the feature.

### Captured directly

| Category | Source | Notes |
| --- | --- | --- |
| `service_call` | `call_service` bus event | Fires before permission checks and before the service runs, so it records an attempted call, not its outcome or authorization. Credential-shaped keys are redacted inside `async_log`. Core merges a call's target block into `service_data`, so non-entity targets (`area_id`, `device_id`, `label_id`, `floor_id`) are extracted into `detail["targets"]` alongside the top-level entity ids. |
| `user_added`, `user_updated`, `user_removed` | the three `homeassistant.auth` lifecycle events | `user_id` is the best-effort acting user (the admin who made the change); the subject is `detail["target_user_id"]`. Earlier releases stored the subject in `user_id`, which made the panel's per-user filter conflate "acted" with "was acted upon". |
| `lovelace_change` | `lovelace_updated` | A dashboard's config was saved. |
| `entity_registry_change`, `device_registry_change`, `area_registry_change`, `floor_registry_change`, `label_registry_change`, `category_registry_change` | the six `*_registry_updated` bus events | For update actions core puts the old values of the changed fields in `changes`, never the new ones, so a rename records only the previous name; the new value must be read from the registry itself. |
| `config_entry_change` | `config_entry_changed` dispatcher signal | Entries added, removed, or updated (including enable/disable). Core exposes this only as a dispatcher signal, so there is no Event and no Context at all; actor attribution is ambient-only. |
| `core_config_change` | `core_config_updated` | Location, name, unit system, timezone, URLs. Core fires this twice during startup with an empty payload (entering `starting`, then `running`); those carry no change and are skipped as noise. A real update passes the changed keys and their new values. |
| `dashboard_panels_change` | `panels_updated` | The payload is empty, so this is a tripwire only: the panel set changed, not which panel or how. Core has no per-dashboard CRUD event. |

HA SOC's own actions are in the same chain (work item 1.4, D-14): `detection_status_changed` and `privileged_read` from websocket_api.py, `firewall_resolved` from firewall.py, `probe_auth_rejected` from probe.py, `soc_config_change` and the user-management records from their handlers, and `audit_chain_reset` from audit.py itself.

### Actor attribution

Nearly every mutation event above is fired by core without a Context, so `event.context.user_id` is None even when an admin clicked the button. Records that go through `_resolve_actor` label how the actor was recovered in `detail["actor_source"]`:

| actor_source | Meaning | Trust |
| --- | --- | --- |
| `event_context` | `event.context.user_id` was populated by core. | The only authoritative source. |
| `ws_connection` | The `websocket_api.current_connection` contextvar identified the WebSocket connection whose command handler this listener ran inside. | Correlational: a contextvar snapshot can leak into unrelated work scheduled downstream of a request, so read it as "this change happened during this user's session", not proof the user made it. |
| `http_request` | The same idea via `helpers.http.current_request`, covering the REST config views (automation, script, and scene editors, core config). | Correlational, same caveat. |
| `system` | No ambient signal: the change came from core, an integration, or a code path that dropped the context. | None. |

Ambient recovery works only because `@callback` listeners run inline in the same asyncio context as the WebSocket command or HTTP request whose handler caused the mutation, and coroutine listeners inherit a copy of that context when their task is created during the fire. The auth events fire inline in the acting admin's WebSocket command task, so `ws_connection` recovery usually works for user lifecycle records; the copied context survives awaits, but the actor is resolved before the first await anyway. A dashboard save arrives over the WebSocket, so it usually works there too. The device and entity registries fire in bulk during integration setup and teardown; those resolve to `system`, which is how an operator separates them from interactive edits.

`_handle_call_service` deliberately has no ambient fallback: `call_service` is the one event where core threads the caller's real Context through, and applying contextvar recovery to the None case would mostly re-attribute automation-driven calls to whichever user's session happened to be upstream, exactly the overclaim the module refuses. Future edits must not let the record imply an outcome rather than an attempt.

`session_seen` is a synthetic record emitted once per refresh token per runtime by `_note_ws_session`, the first time a WebSocket connection is observed through the contextvar. It exists because long-lived access token bearer usage is otherwise invisible; it marks the first observed activity of a session, not its login time, and its absence does not mean the session does not exist. The caveat is stored in the record so an export stays honest on its own. The set of announced token ids (`_seen_ws_token_ids`) is deliberately not persisted: after a restart each still-live session is announced once more, which is cheap and errs toward visibility.

### Best-effort records

No bus event exists for these, so they are reconstructed indirectly:

- `login_fail`: a `logging.Handler` (`_FailedLoginLogHandler`) attached to `homeassistant.components.http.ban` catches the WARNING it logs for every invalid-auth request. This is IP-only: the ban middleware never logs the attempted username anywhere, so `attempted_user` is always None and the module will not fabricate one. It is the only place a failed login is observable from an integration. The handler's `emit()` can run on a worker thread, so it does the minimum (parse a string), hands off through `call_soon_threadsafe`, never calls async code directly, and never raises, because a misbehaving logging handler can wreck whatever thread is logging through it.
- `login_ok`: `_async_poll_tokens` polls every 30 s, diffing each user's refresh tokens against a snapshot (`_token_snapshot` holds `(last_used_at, last_used_ip)` keyed by `refresh_token.id`). A brand-new normal or webhook token, or an existing token whose `last_used_at` advanced, is logged as `login_ok`. A token refresh looks identical to a fresh login through this API, so read it as "this user's session was active". Each record's `detail.new_token` says which branch produced it (True: a token that did not exist on the previous poll; False: an existing token's activity advanced). That is the closest available signal to "a new session began" and the one the `success_after_failures` rule keys on: treating a refresh as a login is what made the rule fire on background activity (work item 3.8). The first poll after start only seeds the snapshot, to avoid a burst of fake logins for every existing session at restart.
- `token_created`: same poll loop; a brand-new long-lived access token id. For long-lived tokens this is the only signal the poll ever produces: core updates `last_used_at` and `last_used_ip` only on the `/auth/token` grant path, which a bearer request never touches, so after creation the poll is permanently blind to that token's activity. `session_seen` is the best substitute for WebSocket sessions.

### Structurally out of scope

- The authoritative acting user behind registry, dashboard, and config mutations. Core fires those events without threading the caller's Context through; the contextvar correlation is the ceiling, and anything stronger needs a change in core (see `UPSTREAM-CORE-PROPOSAL.md`).
- The content delta of an automation, script, or scene edit: the REST config views write straight to storage and fire nothing but a context-less reload service call, and an integration cannot see the request body.
- Which script was reloaded: core has no `script_reloaded` event and the config view calls `script.reload` with no id.
- Config-only updates to helpers (`input_boolean`, `input_number`, `counter`, `timer`, `schedule`, and friends) and lovelace resource add/remove: their storage collections emit no bus event, and their in-process change listeners are reachable only through per-integration `hass.data` keys that are not a stable API, so the module deliberately does not hook them. Helper create/delete and entity renames still surface as `entity_registry_change`; changing a helper's min/max/step/icon fires nothing.
- Whether a request bearing a long-lived access token succeeded: token validation is a pure callback with no side effects, event, or log line; only failures are observable.
- The username behind a failed login attempt.
- Permission-denied errors raised inside a service call or over the WebSocket/REST API: the Unauthorized error is returned to the client with no bus event and no dedicated logger.
- True tamper-proof storage (see `security.md`).

### Storage, flushing, and verification

Storage is newline-delimited JSON, one file per UTC calendar day (`audit-YYYY-MM-DD.jsonl`) under `.storage/<AUDIT_STORAGE_SUBDIR>/`, plus a tiny `chain_head.json` sidecar so the hash chain survives a restart. The sidecar also carries the retention anchor, written whenever retention deletes expired day files, so expiry does not break verification of everything that survives. Records are only ever appended. All file I/O runs in the executor, never on the event loop. Once the current file crosses `_SEGMENT_MAX_BYTES` within a day, records continue in numbered segments (`audit-YYYY-MM-DD.1.jsonl`, `.2.jsonl`, and so on); `_FILENAME_RE` group 2 is the segment index (absent meaning 0), used only to list files in written order, and `_sync_list_day_files` sorts by `(date, segment)`, which equals write order, so verification walks records in the sequence they were appended.

The buffer normally drains on a 30 s timer (`_FLUSH_INTERVAL`), but high-value categories (user lifecycle, HA SOC's own config changes, every `firewall_*` record, `detection_status_changed`, `probe_auth_rejected`, `audit_chain_reset`, `privileged_read`; see `IMMEDIATE_FLUSH_CATEGORIES` and `IMMEDIATE_FLUSH_PREFIXES`, matched exactly or on `startswith`) schedule an immediate flush task instead, so the records most worth tampering with reach the hash-chained files with the smallest window in which a crash could drop them. The set is a public module constant so tests can assert it matches the plan. `async_log`'s `flush=True` forces an immediate flush; the high-value categories get one regardless, so a caller outside the module (probe.py's `probe_auth_rejected`) cannot skip it (work item 1.7).

`_async_schedule_flush` uses `eager_start=False` on purpose: an eagerly-started task would drain the buffer synchronously inside the caller's frame, turning `async_log` from "append and return" into "append, hash, and hand off to the executor" mid-listener. Deferring to the next loop iteration keeps `async_log` non-blocking and lets a burst of records ride one flush (`_flush_task` holds the in-flight task). A done-check is enough dedup: a task that is done has already drained whatever was buffered when it ran. The method is a no-op until the chain head has loaded (`_head_loaded`): before that the instance's seq starts at genesis, and a flush would write records numbered from 1 and clobber `chain_head.json` over whatever chain is on disk. `_sync_load_chain_head` sets the flag first because whatever it concludes, a restored head or a legitimately fresh chain, is the real starting point.

`async_log` is event-loop only and must stay a plain, synchronous, non-blocking callback. `_drain_and_prepare` is likewise synchronous and event-loop-only so the chain's seq and prev_hash mutation never races a concurrent flush. In `_async_flush` the head mirror is written on the event loop after the executor job returns, because `store.data` must never be mutated off-loop; `_seq` and `_prev_hash` cannot have moved since the drain because the flush lock is held and only `_drain_and_prepare` mutates them.

Reset detection in `async_start` must run after the head loads and before any listener can log, so the `audit_chain_reset` record is the first record of the continued chain and carries the mirror's hash as its `prev_hash` (work item 1.5).

The five registries beyond the entity registry each fire their own `<name>_registry_updated` event and share one handler (`_handle_registry_updated`) parameterized with the record category and the payload key naming the changed item. `functools.partial` is safe there because `HassJob` unwraps partials before checking for the `@callback` marker, so they still dispatch inline. Config entries announce changes on a dispatcher signal; `async_dispatcher_connect` returns an unsubscribe callable just like `async_listen`.

Import fallbacks: the literal event-type strings are what core fires; importing the matching constants (`EVENT_USER_ADDED` and friends, the registry `EVENT_*_REGISTRY_UPDATED` names, `SIGNAL_CONFIG_ENTRY_CHANGED`) is a nicety, so an import failure falls back to the stable literal rather than breaking setup. `SignalType` subclasses `str`, so the literal `config_entry_changed` fallback reaches the same dispatcher slot. The `current_connection` and `current_request` contextvars are the only "who did this" signal an integration can read; an import failure degrades to no ambient recovery, never a broken setup. The repairs import in `_async_detect_chain_reset` is local so audit.py's import graph stays minimal.

`async_query` flushes first so a change made seconds ago is visible immediately; `_sync_query` reads only disk, and without the flush the panel would lag up to `_FLUSH_INTERVAL`. `async_category_stats` answers the open-items report's volume observation (a busy install writes on the order of 10 MB of audit records per day) by showing what produces the bulk, so retention and size-cap tuning stops being guesswork. It is deliberately cheap: only the newest day's files are scanned in one pass, with no new storage; it flushes first so buffered records count, and reads as bytes so shares reflect what is on disk. `ws_audit_category_stats` exposes it.

The syslog exporter receives records only after the local JSONL append succeeds and the hash and sequence fields are assigned. The export formats are documented in `CEF-SCHEMA.md`.

## Store and secrets

### The general store

`HaSocData`'s Store holds everything except the audit log: settings, the permissions matrix, and the lifecycle state (new, confirmed, dismissed, resolved) of vulnerability, misconfiguration, scanner, and detection findings. It excludes the audit log and raw event history, which are high-volume and live in their own rotating JSONL files; rewriting one Store file on every audit event would serialize the whole history on every write. It also excludes every secret value.

The one audit-related thing it holds is `audit_head`, a `{seq, hash, at}` mirror of the chain's on-disk head written by audit.py after every successful flush. It exists because the audit directory and the Store are two files an attacker would have to falsify consistently: a wiped or rolled-back audit directory whose head has fallen behind the mirror is detected at the next startup and verification. The mirror only ever advances (`async_set_audit_head`): a backwards head is exactly the wipe signal, so accepting a lower seq would erase the evidence; a regressing call is a programming error or a race and is dropped (work item 1.5).

`_EVIDENCE_FINDING_TABLES` names the three finding tables the evidence retention sweep prunes; the firewall history is a capped list owned by firewall.py and is not swept. `SettingsData` carries no secret values; the frontend's `<key>_set` booleans are derived on the wire by `websocket_api._masked_settings`, never persisted (SEC-1). The firewall default dict has no `addon_secret` key any more; the pairing secret lives in the secret store, and a legacy value is drained on first load.

Other `StoreData` fields:

- `user_baselines`: hour-of-day histograms, seen /24 prefixes, seen destructive domains, the per-user learning-period start, and the privilege-escalation group snapshot.
- `posture_terms`: risk.py stamps terms as their sources become observable; until every term is present the posture result carries `provisional=True`. `async_mark_posture_term_computed` keeps only the first stamp ("computed once ever"): a term that has produced a value stays counted even if its source table later empties, because provisional means "never yet computed", not "currently empty" (work item 3.4, D-10).
- `detections_meta`: runtime facts that must survive a restart, today `{"last_pass_completed_at": ISO}`, written by detections.py and read by risk.py as the `p_detection` evidence.
- `integration_health`: rows `{state, error_count_24h, unavailable_ratio, retry_transitions_24h, domain, title}`, written by health.py and read by risk.py.
- `mfa_grace_started`: cleared the moment a user becomes compliant again, so a future lapse restarts the clock.
- `peripheral_ignored`: a USB or serial device an admin confirmed is intentionally unassigned.
- `firewall`: `known_rules` and `known_rules_reported_at` mirror the add-on's last report; `pending` is the single in-flight test; `history` is a capped log of past applies.
- `integration_security`: `github` caches per-repo signals keyed `owner/repo`; `refreshed_at` is the last refresh.
- `resource_watchdog`: config only; breach counters and usage history are runtime-in-memory, because writing a time series into the Store every sample would churn it for diagnostic data. `hard_limits` is the owner-set Docker cap per slug (`{memory_mb, cpus}`), which requires the Probe's Protection Mode disabled; `hard_limit_state` is the Probe's last report (`{"status": applied|failed|denied, "detail", "at"}`); `overrides` entries are `slug -> {cpu_percent, memory_percent, action, enabled}`, every key optional.
- `panel_layout`: a personal UI preference; any user with SOC access sets their own. A missing `view_id` or `user_id` means "each view's declared default order, nothing hidden", never an error.
- `snmp_status`: operational state, never configuration.

`_async_migrate_func` has no migrations yet; v1.0 is the first shape shipped. `supervisor_user_id` is a runtime-only cache resolved lazily by probe.py on the first inbound Probe call, never persisted, sparing a registry lookup per roughly 5 s poll. `async_load` returns True when a prior save existed, distinguishing a first run from a restart; the old seed-from-`entry.options` consumer was removed with the options mirror (SEC-2), but the flag is cheap and honest information a future first-run step may need. The load merges onto defaults so a Store from an older minor version cannot `KeyError`; because `settings` is nested and the top-level `update()` merges one level deep, settings are re-merged specifically so an upgrading install never misses a key the code and frontend assume (most recently `security_sources_enabled`).

`async_upsert_detection`: when a writer other than the row's own prior state replaces a detection wholesale (the resource watchdog builds a fresh dict with status `open` on every re-trip), the analyst-set lifecycle fields survive; an acknowledged or resolved detection never flips back to open because the same condition tripped again. detections.py passes the existing dict back on update, so the branch is a no-op for it (work item 3.10). `async_set_detection_status` records `status_by`, `status_at`, and `previous_status` on the detection itself and returns the mutated record, or None when nothing exists, in which case nothing should be audited (work item 1.4). `_migrate_legacy_learning_period` copies a stored `risk_learning_period_days` into both rules' `learning_days` slots once (`setdefault`, so an already-set value wins), then drops the key (work item 3.0, D-9).

### The secret store

`secrets_store.py` exists so every secret HA SOC holds lives in exactly one place: a private (0o600), atomically written Store file of its own (`.storage/ha_soc.secrets`). It holds exactly the values behind `const.SECRET_SETTING_KEYS` (external API credentials, the GitHub token, SNMP passphrases) plus the Probe pairing secret under `PROBE_PAIRING_SECRET_KEY`; storing any other key is a programming error and raises (SEC-1). Access is exclusively `await async_get(key)` / `await async_set(key, value)`; there is no dict-style access and no all-values property, so a caller can only obtain the single value it names, at the moment it needs it (SEC-3 relies on that shape). Setting None or "" clears a key rather than storing an empty string. `async_set` saves immediately, not debounced, because secrets change rarely and a crash inside a debounce window must not lose or resurrect a credential.

`async_migrate_legacy_secrets` drains two legacy locations: `SECRET_SETTING_KEYS` values in `store.data["settings"]` and the pairing secret at `store.data["firewall"]["addon_secret"]`. Values are written into the secret store first (saved immediately, so the private file exists before the old copies go away), then the old store is rewritten without them. It runs on every setup and is a no-op once the legacy keys are gone. The `store` parameter is typed loosely to avoid a circular import.

`HaSocRuntimeData.secrets` is the only home of the object: never in `hass.data` under its own key, and its repr prints key names only, so the dataclass stays safe to repr in a debugger.

### Options flow, diagnostics, and Repairs

Every setting is edited from the in-panel Settings tab, gated to the owner. `HaSocOptionsFlow` therefore edits nothing: it is a single informational step pointing at the panel. `HaSocConfigFlow` creates one config entry; HA SOC is install-wide. `_scrub_entry_options_once` rewrites a legacy `entry.options` mirror to `{}` once at setup (SEC-2; see `security.md`).

Diagnostics are intended to be safe to attach to a GitHub issue as-is. Tables holding personal or per-installation detail (users, audit records, findings, permissions) are reported as row counts; a count answers "is the module collecting data" without shipping the data. `_safe_settings` keeps the pre-SEC-1 output shape (every secret key still appears with its `<key>_set` companion); only the source of the presence answer moved. The `resource_watchdog` block includes threshold numbers because they are configuration, not installation data, and reproduce watchdog reports verbatim.

health.py and scanner.py create their own Repairs issues inline because they have the context to do it well. repairs.py covers the cross-cutting issue types: admins without MFA, confirmed high or critical device vulnerabilities, stale long-lived access tokens, and a reset or wiped audit chain (work item 1.5), so none of those modules imports `issue_registry` for a single call site. `async_sync_stale_token_issues` reads straight from `hass.auth` because `UsersManager.async_list_users()` does not include `refresh_tokens` (only `async_get_user_detail` does, one user at a time) and the sync needs every user's tokens in one pass. It is Spook-inspired: a long-lived token unused for 180 or more days is attack surface someone forgot about, since a leaked LLAT never expires on its own. Tokens are not auto-revoked; the issue points at the Users tab's per-token Revoke action. The `TOKEN_TYPE_LONG_LIVED_ACCESS_TOKEN` import uses the layered try/except users.py uses, because the constant's home has differed across core layouts (work item 4.14).

## WebSocket API and access control

`websocket_api.py` is the single surface the panel talks to; the namespace is `ha_soc/*`. Mutating and PII-bearing commands never return raw refresh-token secrets or JWT material, only metadata (ids, timestamps, client names). `require_soc_access` is modeled on `websocket_api.require_admin` (same signature, same "raise Unauthorized, do not call func" shape) so it composes with `@websocket_command` and `@async_response` the way `require_admin` does. The gating tiers are described in `security.md`.

Command notes:

- `ws_version_get` reads the version from `manifest.json` via the loader, the single source of truth core uses for update checking, rather than a second hardcoded string; the Probe's `run.sh` `SCANNER_VERSION` already has to be kept in lockstep by hand and that drift is not worth repeating.
- `ws_users_revoke_all_sessions` returns `revoked` as `{"sessions": N, "long_lived_tokens": M}` so the UI can state exactly what was cleared.
- `ws_detections_set_status` relies on the store handing back the record so the audit entry carries the rule id and transition. An unknown id is an error, not a silent `{"ok": True}`: nothing changed, so claiming success would be false and auditing it fiction (work item 1.4). `ws_detections_bulk_set_status` uses the same gate, applies the per-record bookkeeping to each row, and is audited once with the ids that actually changed, because one record per row would bury the analyst action (work item 3.3).
- `ws_detections_thresholds_get` returns, per rule and parameter, the effective value, secure default, inclusive range, and type, so the Settings tab renders exactly what the server enforces; it is read-only and sits at `require_soc_access`, while changing a value goes through owner-only `ha_soc/settings/set`. `ws_detections_thresholds_reset` clears every override and audits the reset as `soc_config_change` with a per-field diff (work item 3.0, D-9). `_detection_thresholds_schema` is derived from `detections.THRESHOLD_SPECS` so every numeric parameter is `vol.Range`-validated against the same bounds the Settings tab renders; unknown rules or parameters are rejected outright because `vol.Schema` is strict, never stored-and-ignored.
- `ws_settings_set` merges `detection_thresholds` as a partial override per field rather than replacing wholesale, so the Settings tab sends exactly the field the owner touched; the audit record carries a per-field diff against the previously effective value. It validates the complete prospective SNMP configuration (settings plus secrets) before writing either store, so a failed enable or rotation cannot partially apply. `_masked_settings` returns the copy the frontend receives so the form can show "configured" without the raw secret; the wire shape is byte-for-byte what it was before SEC-1, which is why the frontend needed no change.
- `ws_vulns_scan_now` marks the `p_vuln` posture term as computed after a manual scan because a completed scan is positive evidence even when it found nothing, the one case the findings table cannot prove (work item 3.4).
- `ws_dashboard_summary` is one round trip backing the Dashboard KPI row. `ws_network_overview` and `ws_network_security_overview` are one snapshot each backing their whole tab; they never mutate controller state, and a connection problem comes back as `reachable=False` with a readable reason rather than a WS error, so the tab renders a "not reachable" card.
- `ws_layout_get` and `ws_layout_set` implement per-user card order and visibility. This is a personal preference, not a security control, so they sit at `require_soc_access`, and every command reads and writes only the calling user's own layout (`connection.user.id`); there is no "set someone else's layout".
- `ws_firewall_discard_pending`: the archive and the immediately flushed `firewall_pending_discarded` record are written by `firewall.async_discard_pending` so the state machine stays the single owner of the pending slot (D-5).
- `ws_integration_security_refresh` discovers the repo URLs from the current local overview before calling `async_refresh_github_signals`.
- `ws_subscribe` pushes a lightweight refresh ping; the frontend re-fetches the relevant command on receipt. The ping says only that something changed, keeping payloads small and the module decoupled from every consumer's exact shape.

### Permissions matrix

`permissions.py` talks to internal, version-sensitive surfaces: lovelace's runtime `hass.data` container, its dashboards storage collection, and the frontend's per-user storage helper. None is formally public, so every access path is wrapped defensively and degrades to a logged WARNING plus a stable `error_reason` string, both so a version mismatch never crashes setup and so the websocket layer can surface a real message. `PermissionsMatrix` only edits lovelace dashboard configs and per-user frontend storage, and mirrors the intended state into `HaSocData` so the matrix UI and `async_check_drift()` have a source of truth. `_DASHBOARDS_COLLECTION_ATTRS` lists plausible attribute names on the lovelace runtime container, tried in order; the collection is cached once found and never cached negative, so lovelace finishing after `async_start()` is still found. `_find_view` falls back to treating `view_path` as a positional index because real dashboards sometimes omit `path`. `_visible_user_ids` returns None when `visible` is not a per-user list (True or absent means everyone, False means nobody); the caller must tell that apart from an explicit empty list, which also means hidden from everyone. `async_set_view_visibility` builds `expected_policy` where True means "this user should see the view"; users newly listed get True, users dropped from an explicit list get False, and a visible-to-all reset flips previously restricted users back to True. `async_check_drift` is read-only by design.

### Users and MFA policy

`users.py` reads and writes the real auth store (`hass.auth`) and holds no state beyond the in-memory `LiveSessionRegistry`, which reflects live sessions right now (websocket_api.py drives `add()`, `remove()`, `touch()` from the connection lifecycle). Two limitations are load-bearing. First, "last login" is inferred from refresh-token activity (`created_at` / `last_used_at`); a refresh looks identical to a login, so `last_login_at` is "last time this session was active". Second, MFA state can be read and audited but never enforced: core has no hook to require MFA. `account_age_days` is a proxy (the age of the oldest surviving refresh token) because core records no creation timestamp. `credential_age_days` backs the `never_logged_in` factor (work item 3.5): the installed core's `Credentials` model carries no `created_at`, so the `getattr` probe yields None today and only starts reporting if a future core adds the field.

`async_revoke_all_sessions` is the incident-response "lock this account out now" action and includes long-lived access tokens, returning a per-type breakdown. `async_revoke_interactive_sessions` is the post-password-reset revocation (work item 4.12): every normal and webhook refresh token goes, but long-lived tokens are spared because they are not password-derived and silently killing a user's automations on a routine reset would punish the wrong thing.

`mfa_policy.py`: what core does expose is `async_deactivate_user`, a real, enforceable action. So `auto_deactivate` does not pretend to force MFA; once an admin has stayed out of compliance past the grace period it deactivates the account, the outcome a human admin would eventually reach. The default `audit_only` never calls it and leaves enforcement to the Repairs issue and risk factor. `async_enforce_mfa_policy` always runs the bookkeeping half regardless of policy, so switching to `auto_deactivate` does not instantly deactivate everyone already out of compliance; they get a full grace period from when tracking started.

### Panel registration

`async_register_panel` serves the committed bundle (`frontend/dist/ha-soc-panel.js`) as a static path, then registers a custom panel. `_bundle_cache_token_sync` derives the cache token from file content because release archives use a fixed timestamp for reproducibility, so mtime cannot identify the deployed JavaScript; its file I/O runs in the executor. aiohttp routes live for the process lifetime and `async_remove_panel()` only removes the sidebar registration, so a reload must not add the GET route again (`_DATA_STATIC_PATH_REGISTERED`); the `RuntimeError` recovery also covers upgrading from an older build whose route already exists. A failed setup can leave the panel registered, so registration removes any existing `ha_soc` panel before adding the current cache-busted URL.

## Detections and risk scoring

### Rule coverage

detections.py is built only from signals audit.py captures; where the obvious version of a rule needs a signal core does not expose, it is re-derived from the closest real signal or left unimplemented and documented, never approximated. Against the 12-rule spec: (1) brute force per username is not implemented (no attempted username is reachable; `brute_force_user` is never emitted); (2) brute force per source IP is `brute_force_ip`; (3) password spraying is not implemented for the same reason, and approximating it from IP alone would be `brute_force_ip` under another name; (4) success after a failure burst is `success_after_failures`, the one place IP correlation legitimately substitutes for the missing username because the successful event supplies the `user_id`; (5) `new_ip_login`; (6) `off_hours_anomaly`; (7) `dormant_revival`; (8) `privilege_escalation`; (9) `mass_entity_burst`; (10) `token_minting_anomaly`; (11) `disabled_user_activity`; (12) config or diagnostics exfiltration is not implemented because audit.py has no capture path for diagnostics or backup downloads, a known gap rather than a silent omission.

Beyond the spec, `probe_auth_rejected` (HIGH) watches HA SOC's own attack surface, firing from the audit category probe.py writes when a Probe callback fails the Supervisor-context or shared-secret check. At most one detection opens per (caller, hour); every rejection stays queryable in the audit log. The in-pass `emitted` set keeps a burst within one hour from producing multiple upserts for the same row.

Rule semantics:

- `success_after_failures`: with `require_new_token` (secure default on) the success must be a genuinely new refresh token; records from before the `new_token` tag carry no field and are skipped, because "a new token appeared" cannot be proven for them. With `derate_shared_ip` (on) severity de-rates from CRITICAL to HIGH when the IP carried logins from more than one user inside the window (`logins_by_ip` collects `(user_id, ts)` pairs per IP): a shared egress weakens the correlation. A de-rate, never a suppression (D-9, work item 3.8).
- `new_ip_login`: no amnesty; every login since the per-user checkpoint is evaluated. A prefix joins the baseline only after `baseline_days_required` distinct days, entries expire after `prefix_expiry_days` without a sighting, and a prefix is never consulted as trusted in the pass that flagged it (`trusted` is built from the pre-pass snapshot). A maturity gate suppresses flags until `learning_days` of history (`first_login_seen_at`). One detection per (user, prefix) per pass, anchored to the newest triggering login. The first pass for a user seeds silently, because every prefix would otherwise be "new". The pass `now` is both query `until` and checkpoint, so no login is evaluated twice (D-9, work items 3.6 and 3.7). `_network_prefix` follows the address family, /24 for IPv4 and /64 for IPv6 (the standard end-site size), via the `ipv4_prefix` and `ipv6_prefix` thresholds. `_prefix_baseline` grandfathers pre-3.6 plain-list prefixes as `legacy_trusted` rather than re-flagging months of known networks; they still expire. `NEW_IP_LOGIN_MAX_TRACKED_DAYS` (90) caps sighting days per prefix so a long-lived entry cannot grow without bound.
- `off_hours_anomaly`: the first pass fills the histogram and checkpoint without emitting, because the seeding scan spans up to 30 days (`OFF_HOURS_INITIAL_SCAN_LOOKBACK_DAYS`) and emitting would flag a month of normal life. Only events with `context_parent_id` None feed the histogram; automations acting under a user's context must not poison the baseline. A pass covering more than one interval (missed ticks, a restart) scales the burst threshold by `max(1.0, span / interval)` so a catch-up pass cannot fake a burst. The historical ratio includes this pass's own burst, a deliberate conservative simplification (work item 3.7). `_analysis_interval` imports `ANALYSIS_INTERVAL` from `__init__` lazily; the five-minute fallback exists so an isolated import never crashes a rule. `_in_quiet_window` may wrap midnight (the default 23 to 6 does); equal start and end is a zero-length window, an explicit owner choice.
- `privilege_escalation`: the per-user group snapshot is persisted in `user_baselines` (`groups_snapshot`), so an escalation performed while HA SOC or Home Assistant was stopped is detected on the first pass after restart instead of being silently re-baselined as the old in-memory snapshot forced. Only a never-observed user is baselined without comparison. Snapshots of deleted users are purged with the rest of their baseline. `_find_privilege_escalation_actor` returns None rather than guessing (work item 3.10).
- `disabled_user_activity`: bounded to one detection per (user, category) per pass, so a retry loop firing every few seconds cannot mint hundreds of rows out of one stuck tablet; risk.py additionally caps the factor via `risk_cap_points` (work item 3.2).

`DetectionEngine.async_run_pass` reuses the same `users.async_list_users()` snapshot and `now` for every rule so results are internally consistent. The evidence-retention prune is kept out of the rule loop so a rule failure never blocks retention and vice versa. `async_note_detection_pass_completed` is written even when individual rules failed: the posture term reflects that the engine ran (work items 3.3 and 3.4, D-6 and D-10).

Stability: each rule computes a deterministic `detection_id` from `(rule_id, subject, hour bucket)`, so re-running while the same episode is ongoing updates the same row instead of forking one every five minutes; an episode crossing an hour boundary intentionally opens a new row, since "this has gone on for another hour" is worth surfacing. `_upsert_detection` bumps `last_seen` only when the triggering `event_ts` is newer than stored, so re-scanning stale events changes nothing, and `recurrence_count` counts distinct triggering events via `trigger_event_ts`, not passes. A rule with no natural trigger event omits `event_ts` and the pass `now` stands in; a row from an older build has no trigger list and its `last_seen` is the only honest stand-in. `status` is never downgraded by re-detection. `MAX_TRIGGER_EVENTS_TRACKED` (200) bounds the trigger list; overflow only undercounts recurrences (work item 3.9).

Every detection states which rule fired and why in `detail`; each rule's dominant false-positive shape is recorded in `security.md`.

`THRESHOLD_SPECS` is the single source of truth for every tunable parameter (secure default, inclusive range, type via the default). It stays in detections.py because only detections.py and risk.py read it. It transcribes work item 3.0's parameter set exactly; the plan is the authority (D-9). `thresholds(store, rule)` merges stored overrides over defaults; a missing key always resolves to its default, so a partial or older blob can never turn a rule off, and unknown stored keys are ignored. Lookbacks and query limits are deliberately not tunable: they bound how much history a pass reads, and letting an operator shrink them would blind a rule rather than tune it.

### Risk engine

Every score is additive, capped, and explainable. A result's `factors` list is the complete arithmetic behind `score`, sorted so the frontend's top-three chips hide nothing. Nothing infers intent; behavioral factors read detections.py's output and its coverage gaps carry over. `dormant_revival` contributes zero points because its intent is a notification, not a penalty; `mass_entity_burst` has no bespoke factor and only feeds the generic catch-all.

`RiskEngine` has two passes: `async_recompute_all` produces one result per user (static posture facts plus time-decayed contributions from open detections), and `async_compute_posture` produces one install-wide score blending aggregate user risk with vulnerability, misconfiguration, integration health, and open-detection terms. Posture always recomputes risk first so `P_user` is current.

Every factor carries `points` (pre-clamp) and `applied_points` (its share of the clamped 0-100 score), so the list sums exactly to what the user sees. `_reconcile_applied_points` gives each factor its proportional slice rounded to one decimal and folds the residue into the largest factor. Every named factor is capped; the caps for `disabled_user_activity` and `privilege_escalation` are the tunable `risk_cap_points` (defaults 40 and 24) applied with `min` (work items 3.0, 3.2, 3.5). Every threshold, weight, half-life, and cap is a named constant so a tuning pass never hunts for a bare number. Bands: low up to 29, moderate up to 59, high up to 79, critical above.

- `never_logged_in`: an active account with a credential but zero refresh tokens is standing attack surface with no behavioral history. With no tokens there is no `account_age_days`, so the 14-day gate (`NEVER_LOGGED_IN_MIN_ACCOUNT_AGE_DAYS`) applies only where `credential_age_days` is known; today it reports "unknown age" (work item 3.5).
- `long_lived_token_load`: 3 points per token plus a 4-point bonus when the oldest exceeds 365 days, added before the 12-point cap so the cap is the true ceiling.
- Behavioral factors decay as `base * 0.5 ** (days / half_life)` and are dropped below 1 point rather than trickling forever. Resolved detections never contribute.
- `privilege_escalation` is flat: 8 points per detection within 30 days, zero after; "you were just promoted" has no partial-credit shape. `disabled_user_activity` is flat 20 while open and decays with a 7-day half-life once handled.
- `open_detections` counts every open detection regardless of rule, deliberately double-counting "still open right now" against the named factors' "how recently"; capped at 30.
- `_is_public_ip` uses `is_global` rather than `not is_private` because the producing rule already excluded private addresses, and `is_global` additionally excludes CGNAT and other reserved ranges, the real distinction the higher base points (12 versus 8) are for.
- Posture: admins count double in the `P_user` average. CVSS points: critical 25, high 10, medium 4, low or unscored 1; dismissed findings excluded.

Provisional posture (work item 3.4, D-10): the result always carries a score and grade but is `provisional: True` with `missing_terms` until each of the five terms has computed from real data at least once ever. Each term is stamped only on real evidence: `p_user` always, `p_vuln` when findings are non-empty, `p_misconfig` when misconfig findings are non-empty, `p_integration` when health rows exist, `p_detection` when `last_pass_completed_at` is set. Where a clean run is indistinguishable from never running, the term stays missing, erring toward showing the badge longer. Option (a) was chosen: the grade always shows, labeled, because a hidden grade reads as a broken tile. `_maybe_append_posture_snapshot` appends at most one snapshot per calendar day.

### Entities

`SuspiciousActivityBinarySensor` (`binary_sensor.ha_soc_suspicious_activity`) is on while any open detection has high or critical severity; it is the one entity most users automate on without understanding the catalog, and its only attribute is `open_high_severity_count`. `UserRiskSensor` names itself from the user id, not the display name: ids are immutable while names change, and a shared translated name gave every user's sensor the same base entity id, leaving collision suffixes to decide which account was which; eight id characters keep the name readable and unique (work item 3.10, D-19). Entity attribute exposure is deliberately coarse; see `security.md`.

## Scanner and provenance

### Static scanner

scanner.py is not a vulnerability scanner in the CVE sense (vulns.py is) and not a substitute for human review. Every finding is a pattern match against source text, an advisory signal, never a confirmed exploit or a verdict on the author. Nothing is reported upstream; `export_ghsa()` only shapes a finding into GHSA-like fields for a human to copy, a pure function with no I/O.

It exists because hassfest validates manifests, docs, and typing but never pattern-matches code and never runs against `custom_components`; nobody upstream reviews third-party source for security issues. The rule set is stdlib-only (`ast`, `re`) so HA SOC never adds a large, frequently-CVE'd static-analysis dependency. It treats core and custom integrations identically (files on the same filesystem, in the same trust domain as `config/`), reads and never executes them, and makes no network call. Network checks (PyPI staleness, typosquat detection) are a future `scanner_network_checks_enabled` feature and are not stubbed.

Coverage honesty (work plan item 4.8): each completed scan stores a per-domain coverage record alongside the findings, and `listing_payload` exposes it so a domain with no record renders as "not scanned", never as implied-clean zero findings. `_coverage_table` uses `setdefault("scanner_coverage", {})` rather than a store schema change because unknown top-level keys survive the load-time merge. `scan_directory_report` returns `findings`, `coverage`, `scanned_paths` (the only files reconciliation may treat as evaluated), and `candidate_paths` (every `.py` file, so a finding whose file was deleted can resolve). `scan_directory` is a findings-only wrapper kept module-level so the self-scan test can point it at `custom_components/ha_soc` without a running hass.

Resource bounds `MAX_FILE_SIZE_BYTES` (500 KB) and `MAX_FILES_PER_SCAN` (400) apply per integration inside the executor job. When the cap is exceeded, selection is deterministic by size descending with path tie-break: under the old first-N-by-path selection, the large modules that most need scanning were exactly the ones a padded directory could push past the cap. The selected set is scanned in path order for stable output. Skipped files are logged, never silently dropped. The rule loop lives inside the per-file try, so a rule blowing up on one pathological file costs only that file's coverage; a bad file (binary, non-UTF-8, syntax error, or a crafted file driving CPython's parser into RecursionError or MemoryError) is counted as a parse failure. `_dotted_name` walks iteratively because a crafted file can nest attribute access thousands of levels deep.

Rescan reconciliation (`_reconcile_domain_findings`): findings absent from a new scan move to resolved with `not_found_on_rescan`, but only when their file was evaluated this pass or deleted outright, never when skipped (a fail-open guard). A dismissed finding whose pattern is gone from a fully scanned file also resolves, because "the code no longer contains this" is more accurate than "an analyst chose to ignore it".

`_on_config_entry_changed` scans a newly added integration once, off the loop, rather than waiting for the weekly sweep; `scanner_enabled` governs every scan path including this one (the weekly sweep already honored it and the on-install trigger silently did not). `_async_scan_on_install` wraps the task so a raise does not vanish as an unretrieved exception. `async_scan_all` yields between domains because a large install can have hundreds, each a blocking executor job.

A new high or medium finding opens a Repairs issue; an acknowledged extraction finding stays visible but never opens one, because a permanent alarm on a reviewed pattern trains alarm fatigue. When a pass finds nothing the issue is deleted, a harmless no-op or a cleanup. `_hit` accepts an explicit snippet when the source line must not be stored verbatim; the hardcoded-credential rule masks the literal this way (work plan item 1.3). `_RULES` holds the original two-argument rules and `_DOMAIN_RULES` those that need the scanned domain as a referent, kept separate to leave the original signature and its direct-call tests untouched. Rule 1 (TLS verification disabled) matches the keyword name rather than the callee so it catches requests, httpx, and aiohttp alike. Rule 5 includes `AnnAssign` because `token: str = "..."` is the same credential with a type hint. `_entry_mapping_alias_nodes` follows one level of aliasing (`options = entry.options or {}`, and tuple iteration over mappings); `_mapping_use_fires` climbs past defaulting BoolOps; `_call_string_literals` collects literals in source order so a nested path-building call contributes to the outer call's view. Rule semantics and false positives are in `security.md`.

### Device vulnerabilities

vulns.py feeds two checks into `vuln_findings`: firmware currency reads `update` entities with device_class `firmware`, needs no network, and always runs; CVE correlation queries NVD per device, gated by a curated manufacturer-to-CPE table with a noisier keyword search as fallback, best-effort per device. `async_run_scan` never raises: firmware findings are saved even if correlation fails entirely, and one device's failure never aborts the rest. `_scan_lock` serializes scans because the periodic loop and a panel "scan now" overlapping would double NVD traffic (work plan item 4.9).

Correlation matches noisy manufacturer and model strings, not serial numbers or firmware hashes; every match is a candidate for a human to confirm, and absence of a match is not evidence a device is secure, since NVD's coverage of consumer IoT firmware is incomplete. `CURATED_CPE_MAP` is a small manufacturer-only starter table meant to grow toward model-specific CPEs; `_match_curated_cpe` reports vendor-only matches. `keywordSearch` matches description text rather than CPE entries, hence `CONFIDENCE_KEYWORD`; `CONFIDENCE_EXACT_CPE` is reserved and never produced yet. Vendor-only matches report as INFO regardless of CVSS, with the score recorded and a "confirm the model" note. `_severity_for_score` treats an absent CVSS as INFO, unscored CVEs sort last rather than being dropped, and `_extract_cvss` prefers v3.1, then v3.0, then v2, so the score reflects one methodology. `MAX_FINDINGS_PER_DEVICE` (10) takes the highest CVSS first. `FIRMWARE_ONLY_RISK_SCORE` (5.0) is a proxy on the CVSS scale for a device whose only finding is the firmware heuristic.

`_async_query_nvd` pages through offset pagination before ranking, bounded by `NVD_MAX_PAGES` (5) so a whole-vendor wildcard cannot run for minutes under the no-key delay; a vendor with more CVEs has its oldest tail unexamined. A failure on a later page returns the pages already fetched. `MATCH_STRING_CACHE_TTL` (7 days) is in-memory (`_last_fetched`); a restart costs one re-fetch. Only a successful fetch earns the entry, so a transient failure retries next scan. A per-run `run_cache` is shared across devices with the same match string (every Shelly device hits the same wildcard) and records failures too.

`async_device_overview` is a pure read over the device registry and existing findings and never triggers a scan. Risk score is the highest CVSS among open findings; INFO folds into low in the four-column view. Device status buckets (`DEVICE_STATUS_*`) answer only "is Home Assistant hearing from this device right now": `disabled`, `no_entities`, `unavailable`, `partial`, `available`, a separate axis from severity.

### Integration provenance

integration_security.py measures provenance, not safety: an integration is arbitrary Python in-process with no sandbox, and nothing measured proves it is safe. Every surface must say so; the frontend never renders "Safe", "Verified", "Trusted", or a bare shield. Computed locally with no network call: tier (core, HACS-tracked, or unmanaged custom, generalizing HACS's default-store-versus-custom concept to every install path), `quality_scale` and `integration_type` from the manifest, license presence (core inherits HA's license), and scanner findings. GitHub-derived signals (release versus branch, identity assurance, recency, popularity, archived) need an outbound call and an optional token; github_provenance.py gathers and caches them, and this module merges a per-integration `github` block that is None ("not collected") whenever no token is set or no repo URL is discovered. Core domains with an active entry are included so the user sees their whole surface.

Signal 4 variance (work plan item 4.10): only a custom (user-added) HACS repository is flagged, never default-store content, and an unmanaged drop is its own tier. The design also named a `custom_source_list` flag, but HACS runtime data carries only the default/custom split, so that flag is not produced and the module no longer pretends it might be. When HACS internals are not introspectable the source is reported as unverified. `_scan_custom_components_sync` is disk I/O and runs in the executor only; folding the license check into it collapsed one executor hop per integration into one scan. `_repo_url_from_integration` uses `issue_tracker` or `documentation`; core points at home-assistant.io, which yields no repo.

github_provenance.py gathers per `owner/repo`: `has_release` and latest tag, whether the default-branch head commit is cryptographically verified (assurance on the artifact, never "does the maintainer have MFA"), last push, stars and forks (gameable, a weak positive), and archived. With no token nothing runs and every signal stays "not collected"; a token cleared mid-refresh leaves the rest not collected. Results are cached by slug and not re-fetched within `INTEGRATION_SECURITY_CACHE_TTL_HOURS`; `_MAX_REPOS_PER_REFRESH` (60) caps lookups per refresh so one refresh cannot blow an hour's rate budget. An exhausted rate limit stops the loop with `rate_limited` while keeping what was fetched; a `ValueError` from one repo leaves it not collected.

## Health and hygiene

### Misconfiguration sweeps

health.py rests on two approximations. Entity "unavailable ratio" is a point-in-time sample every 5 minutes (`_async_tick`), not a time-weighted duty cycle; exact tracking would need a persistent per-entity listener, and there is consequently no state-change subscription to reverse. Root-logger attribution to a domain (`_HealthLogHandler`, `_async_refresh_attribution_maps`) checks logger names against `homeassistant.components.<domain>`, `custom_components.<domain>`, and each manifest's `loggers` list (longest prefix first); libraries logging under names no manifest declares are dropped rather than guessed. Error counts are attributed per domain and copied onto every entry of that domain. The handler mirrors core's system_log technique: `emit()` does the minimum and hands off via `call_soon_threadsafe`; `_on_log_record` recomputes `error_count_24h` immediately so the count is live.

Finding lifecycle: a finding set to dismissed or confirmed is never flipped back by a later pass; only the resolve path touches status and it skips both. A confirmed finding is an analyst's judgment, and a pass that could not see the condition must not override it. A dismissed finding's Repairs issue is deleted on the next sweep rather than re-mirrored. INFO findings and acknowledged-by-design rows (D-20) never page through Repairs. Every new finding starts as `new`; the store's upsert preserves an analyst-set status (work plan items 4.1, 4.4).

The full sweep runs only after Home Assistant finished starting plus `STARTUP_GRACE`, because components register late and an early sweep would emit a burst of false "broken reference" findings; a reload backdates `_started_at` since there is no startup flurry. `_probe_unreported_since` is in-memory and resets on reload. The merged YAML configuration is loaded at most once per sweep (`_async_sweep_yaml`, `_sweep_yaml_state`: `stale`, `loaded`, `failed`), so the three YAML-backed checks share one load and one WARNING on failure, after which they report could_not_evaluate (work plan item 4.7). `async_run_config_check` (`ha_config_invalid`) runs on its own slower interval: core creates no persistent Repairs issue for invalid YAML, `async_check_ha_config_file()` is purely on-demand, and a full validation is real CPU and I/O work unlike the registry-reading checks.

`async_integration_overview` is computed fresh on every call because the "credential" signal (a pending reauth flow) is transient flow state. Each entry gets at most one category, in priority order: credential, failing (`setup_error`, `migration_error`, `failed_unload`), communication (`setup_retry`), collection (loaded but more than `COLLECTION_UNAVAILABLE_RATIO_THRESHOLD` of entities unavailable), errors (more than `ERROR_COUNT_ISSUE_THRESHOLD` WARNING+ records in 24 h), debug_logging (a domain logger at DEBUG, worth knowing since verbose logs carry sensitive data and are easy to forget), disabled. Credential comes first because a broken credential is usually the root cause of what looks like a communication problem.

`_async_hygiene_finding` is the shared plumbing for every config_hygiene-backed check: one aggregated finding when items exist, none when empty (so the condition clears through the normal resolve path), and nothing touched on could_not_evaluate. Item lists are capped with an honest `total_count`.

Why each Spook-inspired reference check matters: an action calling a service that no longer exists silently no-ops, and for a security automation that is a control that looks configured but stopped doing anything; area, floor, and label references are a weaker signal but still collected; `alert:` references are HIGH because that integration exists to page someone about a bad state, so a broken watched entity or notifier is the single most security-relevant item in the sweep; a notify group missing a member means someone silently stops receiving alerts; a person with a stale tracker works off incomplete presence data that commonly drives arm and disarm; a missing dashboard resource is reliability, not security; a stale `customize:` block is clutter. `_check_notify_coverage_gaps` is HA SOC's own coverage check ("my phone tells me when the fire alarm goes off; make sure I would find out if that stopped working"), split LOW for an untracked source and MEDIUM for one deliberately toggled off (D-11, work plan item 4.4). `_check_broken_entity_references` is entity_remap.py's single-pass scan; 37 of 41 Spook chores are variations on "does this reference an entity that no longer exists", and the README holds the scoping rationale for a curated subset. `_check_probe_addon_not_reporting` is scoped to "installed, running, never once reported", a stuck half-setup with no benign explanation; "used to report, now quiet" would need the add-on's scan interval and a healthy pairing recovers on its own. `_check_ssh_addon_inventory` matches the official slug plus a name substring fallback; absence is not proof. `GENERIC_ISSUE_TRANSLATION_KEY` (`misconfig_finding`) is the fallback Repairs translation key.

### Hygiene helpers

config_hygiene.py returns a `HygieneResult` from every list-returning helper: a list subclass carrying `status` of `evaluated`, `empty`, or `could_not_evaluate`, so existing callers that iterate keep working and health.py branches on the status; an unreadable YAML tree is not evidence a broken alert got fixed (work plan item 4.1). `_merged_yaml_config` is what `alert:`, legacy notify groups, and `customize:` all need; during a sweep it is not called because health.py loads once and passes the tree in, and the `_UNSET` sentinel distinguishes "load here" from "the sweep's load failed" (work plan items 4.1, 4.7). `_walk_service_refs` covers nested `choose`, `if`, `parallel`, and `repeat` blocks naturally and skips templated targets. `_trigger_entity_ids` is automation-only (scripts have no triggers) and narrower than "every entity anywhere" on purpose; device-only triggers are out of scope because `entity_id` exposure is not reliable across targeted core versions. `async_notify_coverage_gaps` excludes scripts because the triggering entity exists only on the automation. `async_unknown_device_references` catches only the gap core does not: core validates device references at setup time, so the check finds a device removed after the automation loaded. `async_notify_group_unknown_members` reads legacy YAML groups through an internal module (degrading to empty if it moves) and the modern config-entry helper; because the entry half always evaluates, the result stays `evaluated`. `async_lovelace_missing_resources` verifies only `/local/` URLs (HACS-managed and external routes are not resolvable through any core API, and absence of proof is not proof of absence) and reads through `async_get_info()` so the sweep does not flip core's own `loaded` flag. `async_orphaned_statistics` and `async_energy_unknown_references` report could_not_evaluate when their data source is absent. A proactive template-mention sweep is explicitly not built; see `decisions.md`.

### Security integrations health

security_health.py has two toggleable sources: entity domains (lock, siren, valve), where "is it working" is a physical-security question, and a curated integration allowlist (kidde_homesafe, elkm1, emporia_vue, unifiprotect, keymaster), reported the same three-way way probe.py and peripherals.py use: not installed, or installed with its state. Enumeration covers both the state machine and the entity registry, because a lock whose integration failed to load has no state object at all, the worst state for a physical-security entity, and must render as `problem: True` with reason "no state (integration not loaded)" rather than vanish; disabled registry entries are skipped (work plan item 4.5). Battery level follows core's own `findBatteryEntity` convention (a sibling `device_class: battery` sensor on the same device); `LOW_BATTERY_THRESHOLD` is 20. "Problem" is narrow: unavailable, unknown, and lock's `jammed`; the module cannot know whether "unlocked" is expected.

### Entity ReMap

Home Assistant has no feature for this in core or in Spook: renaming an entity_id, or an entity disappearing, only touches the registry, and every automation, script, scene, dashboard, and helper keeps the literal old string. entity_remap.py automates the manual step with stated limits. Automations, scripts, and scenes: structured fields are found via core's `referenced_entities` and rewritten by replicating the read, lock, atomic-write, reload primitives core's own config editor views use (there is no importable library function); a reference inside a Jinja template is never auto-rewritten because a regex could corrupt a similar id, so templates are detect-only. Dashboards: storage-mode dashboards are rewritten through `LovelaceConfig`; YAML-mode dashboards are a hard dead end (`LovelaceYAML.async_save()` raises "Not supported") and surface as "manual edit required" with the path; a dict-key occurrence is detect-only because `_exact_replace` rewrites values, never keys. Helpers: config-entry-backed helpers (derivative, utility_meter, threshold, generic_thermostat, generic_hygrostat, integration, min_max, filter, switch_as_x, trend, history_stats, statistics, mold_indicator) store source entity ids as plain fields (`_HELPER_SCALAR_FIELDS`, `_HELPER_LIST_FIELDS`, verified against each domain's const.py and config_flow.py) and are rewritten via `async_update_entry` plus `async_schedule_reload`; template helpers are detect-only; any other entry gets a substring check across `INTEGRATION_LOCATOR_KEYS` and is reported, never rewritten.

`_exact_replace` replaces only an exact match, which is what keeps templates safe. `_apply_scene_fix` refuses when the scene already configures `new_id`, because overwriting would be data loss. `_FILE_LOCKS` coordinates HA SOC's own writers per file; core's editor view locks are not importable, so a simultaneous native edit remains a narrower race, and every write is preceded by a backup. `_apply_yaml_list_fix` re-checks taint inside the lock because the file can change between find and apply; a confirmed id now missing raises `LookupError`. `_load_flat_file_ids` keeps the "will fix" label honest for items split across `!include_dir_merge_list` or packages, which core's own editor cannot edit either; `async_find_references` taint-checks the raw text before any `load_yaml`. `async_apply_remap` re-scans, bulk-rewrites in one pass, and refuses without a server-side backup acknowledgment; reloads happen once per domain for scripts and scenes, while `automation.reload` stays per item with `{"id": ...}`. `async_scan_broken_references` is one linear pass over everything, not one search per entity, and deliberately does not walk dashboards, which the interactive search still covers. Nothing performs a registry rename.

### Container resources, logs, and peripherals

containers.py answers "which container is crashing my server": on a Supervisor install every add-on, Core, and the Supervisor is its own container, and one pinned near 100 percent memory is the classic OOM-kill signal. Stats are fetched on demand through the Supervisor client rather than the hassio integration's cache, which is populated only for add-ons whose disabled-by-default stats sensors are enabled. Fetching is bounded by `_CONCURRENCY` and `_MAX_ADDONS`. A stopped add-on is flagged `not_running` (a container that keeps going stopped is itself the symptom) and gets no stats fetch. Results sort suspicious-first, then memory percent, then CPU.

logs.py's `_MAX_READ_BYTES` makes the fault-log view an advisory glance; the tail answers "did this crash, and how". Container logs come through the Supervisor's journald gateway (transport quirks in `OPERATIONS-NOTES.md`); `async_fetch_container_log` keeps the tail and cuts on a line boundary.

peripherals.py reuses core's own USB discovery data instead of adding host-level device access to the Probe: serial-device visibility is exactly the data core uses to auto-detect a Zigbee or Z-Wave stick, so no add-on and no extra privileges. Scope is serial USB devices (`/dev/ttyUSB*`, `/dev/ttyACM*`, whatever pyserial's `comports()` reports); non-serial peripherals are not enumerated because core provides no such data. Empty results are genuinely ambiguous (no devices, or no `/dev` access), and the empty-state copy says so. `_device_key` prefers vendor, product, and serial because a `/dev/ttyUSB0` path can be reassigned on replug; native ports fall back to `resolved_device`. `_path_mentioned` anchors on a path-token boundary so `/dev/ttyUSB1` never claims `/dev/ttyUSB10` (work plan item 4.13). `_assigned_integration` checks every `INTEGRATION_LOCATOR_KEYS` value because there is no standard field name across zwave_js, deconz, insteon, rflink, and the rest; a miss does not prove a device is unused. `_scan_and_resolve` runs in one executor job because `realpath` through `/dev/serial/by-id` is blocking I/O. The `usb` component is in `default_config` but not a hard dependency, so the overview fails honestly with `available: False`.

### Resource watchdog

The Supervisor exposes no API to cap an add-on's CPU or memory, so by default any add-on can eat the host until the kernel OOM-kills something, often the wrong container. `RESOURCE-WATCHDOG.md` holds the two-layer summary; the mechanics: `ResourceWatchdog` samples per-container stats on an interval and tracks consecutive-breach counts per container against its threshold, so only a sustained breach trips it. On a trip it always records a detection, a notification, and an audit entry, then takes the configured action. Guard rails that are not configurable: Core and the Supervisor are clamped to alert-only (an automated response killing the thing that hosts the automation is a footgun), and after `WATCHDOG_MAX_ACTIONS_PER_HOUR` actions a container is downgraded to alert-only for the rest of the hour, because re-breaching right after every restart is a restart loop. After a trip the counter resets; a stopped add-on's counter is cleared. Hard caps are stored here and applied by the Probe over the firewall poll channel (`async_resource_limits_for_probe`); the module stores intent and result and never touches Docker. Runtime state (`_breach_counts`, `_history`, `_action_times`, `_last_outcome`) is memory-only. `async_installed_addon_slugs` reuses logs.py's cache-backed lookup (work item 2.2).

## Network integrations

### UniFi direct API

unifi.py talks to the console directly over the LAN with an `X-API-KEY` header: no cloud, no extra add-on, no second integration. Everything is read-only. The field mapping is defensive because Ubiquiti ships two overlapping local surfaces with different names, the official Integration API (camelCase) and the older private controller API (snake_case). This build targets the Integration API, but the exact per-field shape of its client and device objects could not be verified against a live controller, so every normalized field is resolved from candidate keys via `_first` and anything absent degrades to None, rendered as a dash; a security tool that shows an honest dash beats one that shows a confidently wrong VLAN. The keys most needing confirmation are in `backlog.md`. `_ACL_ENDPOINT_SUFFIXES` holds only `acl-rules` because the user selected the supported Local Integration API (Network 10.4.57); no private fallback paths are added. The verified contract is `UNIFI-LOCAL-API-CONTRACT.md`.

`_integration_endpoints` is the "tell me when an integration IP fails" feature: `_HOST_KEYS` are config-entry keys that commonly hold a host, matched against client and device IPs, and `_FAILING_STATES` are the entry states meaning "not working"; when two entries share a host, a failing one wins. `_Conn.__repr__` masks the key and keeps host and path; `origin` is scheme plus authority, the base for console deep links; `base_url` appends a constant path. `_normalize_device` gives infrastructure devices the same columns as clients plus device-only extras, enriched from the per-device detail endpoint with `_MAX_DEVICE_DETAILS` capping the fan-out. Gateway selection prefers a device whose role field declares it; name tokens (UDM, UXG, UCG, UDR, and so on) are consulted only when none does, since a switch renamed "gateway closet" would otherwise match (work plan item 4.11). `_derive_wan` walks every plausible nesting and is the single most uncertain mapping in the file; `_fill_network_from_api` treats a listed gateway not explicitly offline as online.

Firewall Policies are genuinely separate from ACL Rules; both are read. `_fetch_acl_rules` probes candidates and returns the first that responds, or `available: False` with the endpoints tried, never a fabricated ruleset. `_fetch_firewall_policies` never probes because the endpoint is confirmed real, so a failure there is a real problem. `_fetch_firewall_zones` returns `[]` when absent so a controller without zones degrades gracefully. `_normalize_acl_rule` surfaces `ports` at the top level as a combined column with source and destination underneath; legacy flat rows still earn a row. `_normalize_firewall_port_filter` surfaces a Traffic Matching List reference as `from_list` rather than fabricating ports; `_normalize_firewall_traffic_filter` models the verified filter types and surfaces REGION, VPN_SERVER, SITE_TO_SITE_VPN_TUNNEL, and IPV6_IID by type alone.

`correlate_server_ports_with_rules` cross-references the HA server's own listening ports (from the Probe) against both rule sets and prefixes labels `ACL:` or `Policy:` so the operator knows which UI to edit. It is conservative: a rule covers a port only when its destination names an IP or CIDR containing one of the server's addresses and its port list is empty or includes the port; a rule scoped to a network or zone is reported as `network_scoped` because the function has no verified way to know which UniFi network the server's IP belongs to; `uncovered` means no rule named the server, not that the port is reachable from everywhere, since the default zone policy still applies. `_ip_in_any` never raises on non-IP filter values; `_server_ip_addresses` never uses 0.0.0.0 or loopback.

`async_network_overview` feeds two sources: the direct API is fetched first and wins where it produced a value; the core `unifi` integration's in-memory state fills blanks and stands in entirely when the API is unconfigured or down. The core snapshot is taken up front so the API path can borrow its WLAN and network maps as fallbacks. `_apply_core_network_data` marks the result as having data when core rows exist while keeping any API error string. `_recompute_client_stats` runs again after enrichment. `_fill_client_row_from_core` never overwrites an API value; bandwidth is core's primary source because the Integration API never returns it. For Protect, `_normalize_camera` surfaces `id` for deep links, a thumbnail that is only a token links to the camera page instead of a broken image, and `_apply_core_protect_data` filters the bootstrap's events to 24 hours (the card is captioned "last 24h"), clears `events_error`, and marks core data as real; `_camera_row_from_core` sets `link` to None without a known origin.

### Core UniFi enrichment

unifi_core.py copies the fields HA SOC needs out of the core UniFi Network and Protect integrations' in-memory state (clients, devices, WLANs, the Protect bootstrap) into plain dicts. Constraints that are absolute: `aiounifi` and `uiprotect` are installed only where the core integrations are configured, so the module never imports them or any `homeassistant.components.unifi*` module; it duck-types with `getattr` and hardcodes the domain strings. `runtime_data` is deleted on unload, so it is read only on loaded entries. Everything is read-only with no I/O. Every access is failure-isolated per entry because this is private core API. `NETWORK_ORIGIN` and `PROTECT_ORIGIN` mark rows built entirely from core memory. `_snapshot_client` reads through library properties where they exist; the wireless-clients registry outranks `is_wired` because it survives the controller's wired bug. `network_snapshot` identifies the gateway as the device owning `uptime_stats` and `network_table`. `resolve_client_vlan` returns the raw VLAN, else resolves through the gateway's table, else the network name. `wan_from_gateway` consults WAN2 only when the primary reported no monitors. `wlan_ssid_map` and `network_name_map` produce the same shapes as the API endpoints they stand in for. `_snapshot_camera` uses the same candidate names `_normalize_camera` reads; `_snapshot_event` wraps the `event.camera` resolver so a dangling camera id cannot sink the snapshot.

### Network security tab and Pi-hole

network_security.py ties together ACL rules, Firewall Policies, the HA server's open ports, and Pi-hole's DNS visibility. `async_network_security_overview` fetches the two read-only snapshots and hands them to `build_findings`, a pure function so it can be unit tested against fixed input; it never raises because both fetchers degrade to `reachable=False`. `_client_summaries` is a lightweight projection (name, ipv4, ipv6, mac, vlan) so the snapshot does not grow a second copy of the full client payload. `_acl_findings` covers ACL-specific findings; `_firewall_policy_findings` adapts the broad-allow check to the zone schema ("broad" means no filter narrowing beyond the required zone pair); `_no_rules_finding` fires only when both sources were read successfully and both came back empty. No finding guesses which UniFi network is "the IoT network" beyond the owner's `pihole_iot_cidr`.

pihole.py exists because the user runs UniFi's DNS so that only the IoT network's clients forward to Pi-hole, making Pi-hole's view the IoT network's view, and because core's `pi_hole` integration exposes only a switch and coarse sensors with no query log, group, or client-scoping surface. `_Conn` is short-lived like `unifi._Conn`: built from the secret store's value, logged in, used, logged out, dropped; its repr redacts the sid. `PiHoleError` surfaces as `reachable=False`. `_logout` never raises. `_TOP_DOMAINS_COUNT` and `_RECENT_BLOCKED_COUNT` (15 each) are display limits, not security bounds (SEC-3).

### SNMP control plane

The integration is the owner-only control plane and secret holder; the Probe is the data plane because it alone shares the host's network namespace. Only SNMPv3 USM AuthPriv is representable; the Probe generates a read-only VACM view and never receives a community string or write credential. `async_config_for_probe` never transmits dormant credentials merely because the Probe is polling. `SERVICE_POLL_SNMP_CONFIG` is a separate poll endpoint so SNMP configuration is never confused with the firewall state machine's `current_test_id` protocol. The contract is `SNMPV3.md`.

## Probe and firewall

### Probe detection and callbacks

probe.py is the boundary between what the integration can see on its own and what needs the add-on. From inside Home Assistant's process a port enumeration sees only HA's own container, even on Home Assistant OS; real scanning needs host-level network access, which `ha_soc_probe` provides. Detection is read-only and uses public hassio helpers; matching is on the add-on's `name:` (`PROBE_ADDON_NAME`), a literal this project owns, because the Supervisor derives the slug from the repository URL the user added. Every caller of `async_probe_overview()` gets a three-way answer: not under Supervisor (structurally unavailable), under Supervisor without the add-on (available but not set up), or the add-on's real state. `_addon_info` imports hassio locally because the module is importable everywhere but only populated on Supervisor installs. `_async_supervisor_user_id` tries the hassio config store first (guarded, since the symbol has moved) and falls through to the auth registry; the id is cached after first resolution. `poll_firewall_command` piggybacks the hard caps on the same channel, attached only when caps are configured. `async_unregister_probe_service` checks for registration first so a Core or Container unload does not log a spurious warning. `SERVICE_POLL_FIREWALL_COMMAND` uses `return_response=True` on an ordinary service call rather than a new listening port on the add-on, because scanner.py already treats extra listening sockets on a security tool as the wrong default.

### Firewall state machine

Everything else in the project is advisory; firewall.py is the one deliberate exception. It answers "let me change which ports are reachable from where without locking myself out". Three properties make that safe: every rule lives in one dedicated chain (`HA_SOC_RULES`), never INPUT directly and never anything Docker manages, with a full `iptables-save` backup before every apply as defense in depth; a proposed ruleset is "testing" for `DEFAULT_FIREWALL_TEST_WINDOW_SECONDS` and becomes permanent only on explicit confirmation; and the auto-revert timer lives entirely inside the add-on process, a local `sleep N && restore-unless-confirmed` armed the instant rules are applied, so if the new rules break the channel Core uses to reach the add-on, nothing depends on that channel to revert. Core proposes and displays; the add-on's own report is always the final word.

One test at a time (`async_propose_test`): while `pending` is occupied, whatever its status, a new proposal is refused with `test_pending_unreported`, even for a record already relabeled `expired_unreported`, because until the add-on's report or the owner's discard archives it Core does not know what is live on the host. Only two paths clear `pending`: `async_report_from_addon` and `async_discard_pending`. `_lazily_expire_if_stale` is display-only. When the add-on later polls holding no test, that is the evidence its timer reverted, and the record is archived as `reverted` by `addon_timer`. A poll holding a different id is answered `none` with `addon_holds_other_test` so test B is never applied while test A's timer is running against the same chain. `async_next_addon_command` compares against the add-on's own `current_test_id` rather than trusting Core's record, which keeps it correct across missed or out-of-order polls. `async_confirm_test` marks intent immediately and does not archive, so a test is never archived twice. The countdown is re-anchored at apply time: `expires_at` starts as propose time plus the window (bounding a stale proposal) and is recomputed to `applied_at` plus the window when the apply is handed out, so the panel tracks the add-on's real timer (work plan section 2). `async_discard_pending` (D-5) refuses with `no_pending_test` or `window_not_lapsed`; a lapsed countdown means the add-on's own timer has also fired if it is alive, and a record without a parseable `expires_at` is discardable immediately. Archived entries are copies. `_mark_rules_partial_ipv6` returns copies because `partially_applied` is computed at read time. `_async_runtime_audit` fetches the audit log at use time; in tests without an entry the report path goes unaudited rather than crashing. The backup checkbox is enforced server-side, because a client-only gate on a destructive action is not a gate. `FIREWALL_TEST_EXPIRED_UNREPORTED` and `FIREWALL_TEST_DISCARDED_UNREPORTED` are named for the load-bearing "unreported" half: Core never learned from the add-on what happened on the host.

### Probe add-on services

The Dockerfile pins `ghcr.io/home-assistant/base:3.24` by its immutable digest because the tag is moving; the tag stays so a human sees which release the digest froze (work item 2.5). `iptables` is needed because the firewall feature requires the real binaries, not busybox stubs; `iproute2` provides `ip -4 -o addr show` for bind-address resolution and is pinned rather than relied on by accident; `apk upgrade` runs before adding the runtime because Alpine fixes continue after the digest; only the `net-snmp` agent is installed; TempIO is removed as unused attack surface. security.yml's "Verify the minimal SNMP runtime" step asserts all of this.

The port scanner (`services.d/ha_soc_probe/run`) reports the host's real listening TCP ports, which works only because `host_network: true` makes `/proc/net/tcp[6]` the host's table. It reports port and protocol only: process attribution needs `host_pid: true`, a privilege the add-on does not request. The scan loop runs as `nobody`; only secret creation and `bashio::config` run as root, handing their results down through exported variables and re-execing under `s6-setuidgid nobody` (work item 2.5). A rejected report (commonly HTTP 400 while the integration is not loaded yet after a Core restart) enters a capped-exponential retry loop (30 s doubling to 300 s) with a clear log line, instead of waiting out a scan interval that can be 24 hours. s6 stops the service with SIGTERM on every stop, restart, and update; without a trap bash dies mid-sleep and the finish script logs a crash, so the trap sets a flag, every sleep is a backgrounded `sleep` plus `wait` (which a trapped signal interrupts immediately), and the loop exits 0 at the next checkpoint. The finish script treats exit 0 as a routine stop and anything else as a crash s6 restarts. The decoding helpers use busybox awk only (no `strtonum`); `build_interface_map` degrades to `unresolved` interfaces if `ip` is unavailable; IPv6 addresses are left null rather than risk a wrong decode.

The firewall poller (`services.d/ha_soc_probe_firewall/run`) is the only thing in the add-on that mutates host state. It polls `ha_soc.poll_firewall_command` every 5 s. On `apply` it validates every delivered field locally first (the add-on must never be an arbitrary iptables client even for a compromised Core), takes backups for both families and checks each succeeded (a full filter-table dump per family for manual recovery, and a chain-only snapshot per family that a revert replays), refuses the whole test as `reverted` / `backup_failed` if any backup fails, replaces the `HA_SOC_RULES` chain contents in each table, and arms the local revert timer. The apply is atomic across families: if any rule fails in either table, both are restored from snapshots (work items 2.3, 2.4, 2.5). On `confirm` or `revert` it marks the test resolved (making the timer a no-op) and reports immediately with `firewall_ipv6_supported` and an optional bounded reason. On startup an unresolved test is treated as failed and reverted, since its window length is unknown. On SIGTERM it exits 0; the finish script, not the trap, performs stop-time recovery (work item 2.6), and the per-test resolved marker keeps that revert exactly-once across timer, finish, and next start. Reverts are chain-scoped (flush and replay `-A HA_SOC_RULES` lines, skipping `-N`) and never `iptables-restore` over a whole table, which would roll back Docker's rules; a missing IPv6 snapshot leaves that chain as-is with an error logged. IPv6 support is probed per cycle with `ip6tables -S`, never cached; `ensure_chain` re-runs before every apply because support can appear after start. `apply_ruleset` is flush-then-apply of the full desired state; `known_rules_json` is the real union of both chains, one entry per table a rule is live in. A resolved id is cleared at the top of each cycle so Core's one-test gate does not wedge, and a fresh state read before an apply refuses a second test while one is armed. The finish script mirrors the run script's revert machinery and must change in lockstep; reporting there is best-effort because the Supervisor proxy may already be tearing the container down.

Resource hard caps arrive on the same poll channel and are applied against the Docker socket; because the Supervisor recreates containers on update or restart, dropping Docker-level limits, caps are re-applied every `LIMIT_APPLY_EVERY` cycles (about 60 s) and immediately when the set changes, and removed caps reset containers. `apply_resource_limits` never exits non-zero; each slug reports `applied`, `failed`, or `denied`. `resource_limits.sh` holds the pure validation and serialization helpers so CI can exercise hostile payloads without a socket. The SNMP supervisor service takes configuration only from `ha_soc.poll_snmp_config`; an unchanged generation carries no credentials and just restarts snmpd if needed.

## Frontend

### Shell and navigation

`WORKSPACES` in nav.ts is the console's stable information architecture: leaf tab ids remain unchanged so stored layouts, navigation events, and backend authorization contracts do not migrate; only the shell groups related tools into six workspaces instead of one long list (see `FRONTEND-VISUAL-ARCHITECTURE.md`). `HA_SOC_NAVIGATE` is a bubbling, composed event that crosses shadow DOM up to `<ha-soc-panel>`, the owner of tab state; `clientFilter` pre-fills the target tab's search box (only the Network tab's Clients table consumes it, once, after which the panel clears it). `navigateHa` navigates elsewhere in core's frontend without a reload by pushing history state and firing `location-changed`, the pattern third-party panels use, because a custom panel's module runs in the same document (`mainWindow` resolves to `window` for a non-iframe panel_custom). Only `/config/devices/dashboard` with `?config_entry=` or `?domain=` is verified; no availability or state filter exists via URL, and the entities dashboard's status filter cannot be preset either.

In ha-soc-panel.ts, `_customizeMode` is transient editing mode, not persisted, reset on tab change. A denied access call surfaces as a rejected `callWS` and is treated as `allowed: false` rather than leaving the panel loading or rendering tabs that 401. The footer's two info commands are plain `require_admin` so the footer renders on the "Access restricted" screen, best-effort. The Settings tab is never rendered for a non-owner as defense in depth.

The shell also owns staleness detection: `loadedBundleToken()` reads the `?v=` cache token from `import.meta.url`, and `_bundleIsStale()` compares it with `panel.config.bundle_token`, which `panel.py` sets from the same SHA-256 digest it appends to the module URL. A mismatch renders a reload banner above the header. The comparison lives in the frontend because only the browser knows which bundle it actually executed; the server cannot see that. Operational detail is in `operations.md` under Panel bundle.

### Customize layout

`CustomizableView` is the base class for card-based views participating in Customize: it loads and saves its own layout and renders the declared sections itself, in stored order with hidden sections removed, so a view implements only `viewId` and a `LayoutSection[]`. The section templates must render inside the view's own shadow root: `sharedStyles` and each view's card, table, and chart rules are adopted there and nowhere else, so a section rendered inside another element's shadow root loses every visual style and collapses to unstyled text. `<ha-soc-customize-list>` is therefore the editor only and is rendered in place of the sections while Customize mode is on. A view that does not participate keeps extending LitElement; Settings is the example, because hiding a config form card would hide controls. Layout loading is best-effort and saving is fire-and-forget. `<ha-soc-customize-list>` owns reorder and show-hide mechanics; it shows a compact chrome list (title, handle, Up/Down, Show/Hide) rather than live-dragging full cards, which can be large tables. Up/Down are real buttons so the feature is keyboard-usable, with native drag as a progressive enhancement; both converge on `_move()`. `LayoutSection.render` is typed `unknown` because renderers may return lit's `nothing` sentinel; `hideable` is false for a section whose hiding would leave the tab pointless. `resolveSections` drops stale stored ids and appends new sections at the end so a future card is never silently hidden.

### Shared helpers

sortable.ts exists as one module for its accessibility contract: the `<th>` carries `aria-sort`, the clickable element is a real `<button>`, the arrow is `aria-hidden`. `nextSortState` cycles unsorted, ascending, descending, ascending. `sortRows` is stable; null and undefined always sink regardless of direction (unknown is not smallest); numbers compare numerically, everything else case-insensitively. styles.ts builds on Home Assistant's own CSS custom properties so the panel follows theme. types.ts declares only the `HomeAssistant` surface the panel touches (`callWS`, `connection.subscribeMessage`) rather than vendoring frontend's types.ts. device-match.ts resolves a rule's IP, MAC, or CIDR against the client list; only IPv4 CIDR containment is resolved (IPv6 needs 128-bit arithmetic), bare addresses and MACs are exact matches, and callers should cap how many matches they display. firewall-matrix.ts is a pure zone-by-zone summary matched by zone name (the policy row carries no id); "dominant" describes what is there, never which policy wins, because UniFi's ordered evaluation with implicit deny was not verified well enough to claim a winner; "mixed" means both ALLOW and BLOCK/REJECT exist.

### Data layer

ha-soc-ws.ts wraps every `ha_soc/*` command. `fetchSystemLog` and the container-log command are called as core commands directly because `system_log/list` is admin-gated on its own and the panel already gates tab content on `ha_soc/access/info`. Each fetcher mirrors the server module it names, and the types carry the same honesty: `fetchProbeOverview` is a three-way answer; `fetchIntegrationSecurityOverview` reports provenance; `fetchPeripheralOverview` rests on core's USB discovery; `fetchEntityRemapReferences` labels every reference editable or not and nothing implies a fix until apply returns; `fetchLayout` and `saveLayout` touch only the calling user's layout.

### Views

The error-state convention (work plan item 4.12): every view keeps a distinct `_error` that renders a could-not-load state carrying the server's message and a Retry button, so a failed load never looks like an empty result, a stuck "Loading..." page, or a real backend "not available" state. Three real bugs came out of that pass: settings-view and integration-security-view had no catch around their outer fetch, peripherals-view rendered a failed call as the false claim that USB discovery was disabled, and entity-remap-view's broken-references load could stick on "Loading..." forever.

- Audit: the users lookup is loaded once, not per filter change; stats are fetched on demand because the server scans the newest day's files each call; Time sorts by parsed timestamp and User by resolved name. `AUDIT_CATEGORIES` must track every category audit.py can write. The chain-verify message avoids a bare "intact" when `verified_from_seq` is greater than 1.

## CI and release

Every `uses:` reference is pinned to a full commit SHA so a moved or compromised tag cannot change the code a workflow runs; the matching release is recorded in a trailing `# vX.Y.Z` comment reviewed on Dependabot updates, and where upstream publishes no tags the comment records the ref and date. `build_compliance_evidence.action_pinning_findings()` reports any unpinned action (work plan item 0.6, CI-1). test.yml declares `workflow_call` so release.yml reuses the exact pytest and bundle-drift jobs as its release gate (`needs: tests`) instead of a second copy that could drift; both jobs also run on every push and pull request. Workflow tokens are `contents: read` at the top level; jobs needing more request it per job, and prepare-release.yml uses a short-lived GitHub App token only for the `automation/calver-release` branch. Node 22 is pinned in `setup-node` because package.json declares no `engines` constraint. The bundle-drift job exists because HACS serves the committed `dist/`, so it runs `npm ci`, `npm run build`, and `git diff --exit-code dist/`. validate.yml catches the class of problem that broke a HACS install (an unparseable manifest or hacs.json, a missing key, a bad domain), pinned to the head of hacs/action's `main` and home-assistant/actions' `master` on 2026-08-30 because neither publishes tags, and runs weekly to catch HACS requirement drift. pytest pins live in requirements-test.txt so Dependabot can update them; per D-16 CI tests only the pinned latest harness. CodeQL resolves the v4 tag to a commit and uses `build-mode: none` for both languages. The Probe image is scanned with a pinned Grype and HIGH/CRITICAL findings fail the PR. ShellCheck is told `--shell=bash` because the s6 scripts use a `with-contenv bashio` shebang, and SC1091 is excluded because the sourced helper path exists only in the image.

release.yml reconciles the version on main into a complete GitHub Release; a merge is the trigger and maintainers never push tags. Reruns are safe: a published version stays immutable and a draft is resumed. SBOM generation uses anchore/sbom-action and attestation uses actions/attest twice (provenance and SBOM). Immutable releases lock tag and assets at publication, so the sequence is create the tag ref, create a draft, attach assets with `--clobber`, publish. prepare-release.yml turns release-bearing changes on protected main into a tested CalVer bump PR, as described in `automated-calver-release-design.md`. compliance-evidence.yml runs monthly and on dispatch, records branch protection from the branch endpoint, needs an optional Administration-read token to observe the immutable-releases setting (otherwise recording `available: false`), keeps code-scanning alerts as counts by severity only, and fails the final job when collection is incomplete after preserving the partial pack.

scripts/release.sh prevents the bug where the manifest version, add-on version, and tags drifted apart (a mismatch shows as "wrong version" or as `custom_components/None/manifest.json`); it bumps every version in lockstep and opens an auto-merge PR. Versions are `vYYYY.MM.DD.V`; the v prefix is canonical wherever a person reads it, while the three machine-read fields carry the bare number, and the workflow enforces `tag == "v" + manifest version`. Automatic revision selection considers both existing tags and the current manifest so a bumped-but-untagged version never versions backwards. scripts/ha_soc_verify_supervisor.sh (D-21) verifies the Probe's platform facts on a real Supervisor read-only; it discovers the container by name rather than assuming `addon_<slug>` because auto-update recreates the container.
