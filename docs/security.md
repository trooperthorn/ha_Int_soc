# Security

Trust boundaries, enforced versus cosmetic controls, secret handling, redaction rules, audit chain integrity reasoning, and the false-positive and evasion notes for detections and scanner rules. The threat table itself lives in `THREAT-MODEL.md`; this document holds the mechanism reasoning behind its rows.

## Trust boundaries and gating

### WebSocket tiers

Every `ha_soc/*` command is gated by `@require_soc_access` (admin, plus HA SOC's own `access_level` setting), regardless of the panel being registered `require_admin=True`; panel visibility is cosmetic, so the real gate is the websocket layer. A security-posture tool is itself a high-value target, so it defaults to owner-only. The one exception is `ha_soc/access/info` (and `ha_soc/version/get`), which stay on plain `require_admin` so an admin locked out by `access_level` can still ask why, instead of every command silently returning unauthorized.

Above that baseline sit two owner-only tiers. `@require_owner` refuses a non-owner admin even under `owner_and_admins` (D-4, D-5, D-23):

| Command group | Why owner-only | Enforced or cosmetic |
| --- | --- | --- |
| `settings/get`, `settings/set`, `detections/thresholds_reset` | They hold the security-sensitive controls, including the access level and API credentials; the reset rewrites the same stored setting. | Enforced, verified by test_access_control.py |
| Every firewall command, status included (D-4) | A firewall change can end with the platform unreachable, and reading the ruleset maps the attack surface, so no account but the owner may even look (see `THREAT-MODEL.md`, "Firewall control access gating"). | Enforced |
| `watchdog/set` | Enforcement controls: a bad threshold auto-restarts add-ons and a hard cap changes host containers. | Enforced |
| `entity_remap/apply`, `permissions/sidebar/push` (D-23) | Both rewrite configuration or per-user policy, the same takeover surface D-4 closes. Finding references stays open to admins. | Enforced |

The second tier is conditional, applied inside the handlers via `_async_target_is_admin`: `users/update`, `users/deactivate`, `users/delete`, `users/revoke_token`, and `users/revoke_all_sessions` become owner-only whenever the target is an admin-group user (the owner or a `GROUP_ID_ADMIN` member), resolved server-side from `hass.auth`. An admin who can cut off other admins through HA SOC can take the platform over; a non-owner admin keeps those commands for non-admin targets, so the admins tier still means routine user management. `users/update` is included because the general endpoint must not demote, deactivate, or rewrite the owner or another administrator. The check never trusts anything the client sent beyond the user id, and it looks at group membership rather than `User.is_admin`, because `is_admin` is False for a deactivated admin-group user, exactly the account this gate still protects. An unknown id returns False so the command's own not-found handling answers, disclosing nothing beyond the id's absence (D-23 option (a)). `ws_users_update` also refuses `is_active: False` for the owner even when the owner asks, because core's dedicated deactivate path protects the owner but `async_update_user` accepts `is_active` directly.

Home Assistant's native Configure dialog is a weaker door than the panel: core gates it with a generic admin check and never tells the flow which user is driving it, so it cannot enforce the owner-only rule. Editing the access level or credentials through it was a real authorization bypass, which is why the options flow now edits nothing. Older builds also mirrored every settings save, secrets included, into `entry.options`, which lands in `.storage/core.config_entries`, a world-readable file; nothing reads that mirror any more, setup scrubs a legacy copy to `{}` once (logging key names only), and `HaSocOptionsFlow` always creates the entry with `data={}` so a save through the dialog can never repopulate it (SEC-2).

### Cosmetic controls

Everything in permissions.py is cosmetic. Setting a view's `visible` list, flipping `require_admin` / `show_in_sidebar`, or pushing `hiddenPanels` only changes what a user's own frontend renders. None of it is enforced by the backend: any authenticated user can call `lovelace/config` for any dashboard `url_path` and get its full configuration; there is no permission check on that command in core, and nothing in the module changes that. The only real enforcement lever for "should this user reach X" is the admin / non-admin split on the account, handled in users.py. `permissions/sidebar/push` is still an admin acting on another user, so it is audited with the target and the full hidden set. `require_admin=True` on the panel hides it from non-admin sidebars; it never protects data.

In the frontend, owner flags and disabled buttons are cosmetic and only prevent dead clicks; the server resolves the target and enforces regardless. The tab gate fails closed: a rejected `ha_soc/access/info` call is treated as denied, `_isOwner` in every view defaults to false and stays false when the lookup fails, and the Settings tab is never rendered for a non-owner. Core commands (`system_log/list`, container logs) are called directly because core already admin-gates them and the panel gates all tab content first.

### User management guards

`async_update_user` refuses to deactivate the owner as defense in depth for callers outside websocket_api. `async_delete_user` guards the owner and self-deletion, because core's `async_remove_user` does not block removing the owner, which would leave the instance with no owner at all. `async_set_password` mirrors core's `admin_change_password`: owner-only, and the check must not be weakened. A password reset revokes the target's interactive sessions by default; whoever held the old password must be signed out or the reset changes nothing for an attacker with a live session; long-lived tokens are spared, and opting out is explicit via `revoke_sessions: false` (work item 4.12). The in-panel password field is a real masked input, never a plain-text browser dialog.

The MFA policy never evaluates the owner: core refuses to deactivate the owner (`async_deactivate_user` raises `ValueError`), and locking out the one account that manages the install would be a self-inflicted outage. `_is_noncompliant` treats a missing `mfa_assessable` field as True; failing open would widen the exemption to every stale payload, and the D-18 exemption applies only when users.py positively established that every credential comes from a non-homeassistant provider.

### Entity attributes

Entity states and attributes have no per-user ACL in core; any authenticated user, including a non-admin local-only account, can read them, while every `ha_soc/*` command is gated. So `PostureScoreSensor` exposes the grade only: the per-term breakdown maps exactly where the install is weakest and stays behind `ha_soc/risk/posture` (work item 3.10, D-19 option (a)). `UserRiskSensor` exposes `band`, not `factors`, because a factor list can include another user's MFA status, token count and age, and flagged behavior; `band` is coarse enough to automate on without disclosing why.

### Probe callbacks

The Supervisor system-user context is the primary gate on every inbound Probe service call; the shared secret is defense in depth. A call whose context user is missing or is any account other than the Supervisor user is rejected before its payload is looked at, audited as `probe_auth_rejected`, and surfaced as a HIGH detection; a None Supervisor id at call time means the user genuinely does not exist and nothing may pass. This covers a forged call from another user's session and a context-less call from an automation. On rejection nothing is processed, not even `open_ports`: an unauthenticated caller must never be the one that pins the probe secret. Rejections are logged at WARNING at most once per caller per 10 minutes so a polling forger cannot flood the log; the audit record is written every time. The firewall poll handler returns an empty answer rather than an error, so a forger learns nothing about pending work. On Core and Container installs the services are not registered at all.

`async_verify_or_pin_secret`: the add-on generates a random secret once, persists it in `/data`, and sends it on every call. Core pins the first non-empty secret it sees on a call that already passed the context check, then requires an exact match, so the first-caller-pins race the old trust-on-first-use design had is closed to anything that cannot call through the proxy. A missing secret is always a rejection; the old branch that accepted "nothing pinned and nothing presented" is gone because it let any local caller through until the real add-on's first report. An add-on too old to send a secret is rejected until updated, and the owner-only pairing reset is the recovery. The comparison uses `hmac.compare_digest` so a forger cannot learn the pin byte by byte through timing. The pin lives in the private secret store under `PROBE_PAIRING_SECRET_KEY`, fetched at use time (SEC-1).

### External audit ingest

`ha_soc.ingest_audit` reuses the Probe's two gates: the Supervisor user's context
on the call, and a per-source secret pinned on first use. Both are enforced. What
the chain check adds is integrity of the delivered history, not authenticity of
its content: a source that lies consistently from its first record produces a
valid chain. What it defeats is editing, truncating, or reordering a source's
log after the fact, because HA SOC holds the head it last accepted and every
break, gap, or rewrite is recorded in HA SOC's own chain and raised as a HIGH
detection. Trust-on-first-use means the first caller for a source name owns
that name until the secret store entry is cleared; the source slug is
validated, and the record schema caps sizes so a hostile caller cannot fill
the audit directory faster than the retention sweep.

### The add-on treats Core as hostile

The integration validates every firewall field at its WebSocket layer, but the add-on revalidates every field before any iptables argument is built, because the threat model for a NET_ADMIN process includes the case where Core itself is compromised. Each check (`valid_action`, `valid_proto`, `valid_family`, `valid_port`, `valid_window`, `valid_source_for_family`, `validate_ruleset`) is a strict allowlist; a failure refuses the whole test before the chain is touched. The window bounds exist so a compromised Core cannot park unconfirmed rules on the host for a day. The source check is a shape allowlist (only the characters an address plus prefix length can contain, bounded in length, with the family consistency Core's schema also derives), keeping shell and iptables metacharacters out; iptables is the final judge of the address, and a rule it rejects fails loudly (work item 2.5). Core-side, `_valid_source` validates a real IP or CIDR so a typo cannot sail through to the add-on, where a malformed `-s` argument would silently fail and leave the operator believing a restrictive rule is live.

A delivered test id becomes file names under `/data`, so the same slug allowlist Core's uuid hex ids satisfy (`^[a-z0-9][a-z0-9_-]{0,63}$`) keeps path syntax out; no report is possible for an id the add-on refuses. The same regex guards add-on slugs before any Docker URL is built, and it is enforced at both ends: the WS schema restricts `override.slug` and `hard_limit.slug`, the handler requires the slug to name an installed add-on, and the Probe re-checks locally, so a compromised Core cannot steer the Docker client at an arbitrary container (work item 2.2). Every slug loop is a quoted `while IFS= read -r` over jq output, never an unquoted `for $(...)`, because an unquoted loop word-splits whatever a compromised Core put in the JSON. The pure helpers in `resource_limits.sh` validate the complete delivered and persisted documents before any Docker URL or body is constructed, because the firewall process holds the Docker socket.

Why NET_ADMIN, and why it is contained: a real CAP_NET_ADMIN is the only way a container can run iptables against the host's tables, Protection Mode or not. Every rule lives in the dedicated `HA_SOC_RULES` chain plus exactly one jump at position 1 of INPUT (`iptables -I` with no index), ahead of Docker's rules and anything the host had, because a deny that sits below an accept is not a deny; if the jump sat after a broad accept, every deny would be cosmetic while the panel claimed enforcement (work item 2.4). Reverts never use a whole-table restore, which would roll back Docker's rules too; the unquoted `${line}` expansion in `replay_chain_backup` (SC2086 disabled) is deliberate because the line is iptables' own `-S` output for a rule this script wrote, and none of its arguments contain whitespace. A failed backup refuses the test outright, because a test whose revert path cannot be guaranteed must never be applied.

Declaring `docker_api` sets the Supervisor rating to 1 unconditionally, a deliberate documented choice: one companion carries every host capability the SOC needs. With Protection Mode on the socket is not mounted and every cap application reports `denied`; applying caps requires disabling Protection Mode on this add-on, a root-equivalent grant the panel spells out first. Process attribution for listening sockets is deliberately not requested (`host_pid`). The live install records `signed: false`, accurate for a locally built add-on; the base-image digest pin is the compensating supply-chain control.

The shared probe secret is created by whichever service starts first under `umask 077` with `noclobber`, so racing services cannot end up with two values; every service also `chmod 600`s a pre-existing file because the first live verification run found it at 0644. The port scanner's root block does only secret creation and `bashio::config`, then re-execs as `nobody`; the secret file stays root-owned at 0600 and its value is handed down in an exported variable, the same channel `SUPERVISOR_TOKEN` travels in. The re-exec goes through `bashio "$0"` rather than `"$0"` because the shebang's `with-contenv` half re-reads `/run/s6/container_environment/*`, whose readability as `nobody` is not a verified fact, and the current environment already carries everything. If `s6-setuidgid` is missing the scan runs as root with a logged warning rather than crash-looping.

SNMP hardening: a daemon-specific `ha_soc_snmp` account (no home, no shell) keeps the `nobody` scanner from reading Net-SNMP's mode-0600 localized USM key database; configuration arrives only from the owner-only settings service and represents only SNMPv3 USM AuthPriv; disabling is credential retirement (runtime config and USM database deleted); the listen address must be assigned in the shared namespace and never 0.0.0.0 or `::`; plaintext passphrases exist only in the mode-0600 createUser file during snmpd's initialization window; snmpset and tempio are absent. The safe-token constraint on usernames and passphrases keeps values unambiguous in snmpd.conf and prevents injection at the Probe boundary; dormant credentials are never transmitted merely because the Probe is polling.

### CI

Read-only workflow tokens, SHA-pinned actions, and the App-token split in prepare-release.yml are the controls against a compromised step or a moved tag. Bandit runs at `-ll` with B104 (binding to all interfaces) skipped because it flags the intentionally all-interface probe listener; the add-on firewall and the authenticated request boundary are that listener's controls. The compliance evidence pack retains code-scanning counts by severity only, never alert paths, descriptions, or source excerpts. The Probe image is scanned with Grype at every push and HIGH/CRITICAL findings block the PR.

## Secret handling

### What the secret store buys

The secret store is not protection against a hostile integration: integrations are modules in one Python process with no isolation, so in-process code can still reach the object through runtime data and call `async_get()`. What the design buys: fewer copies (one file and one in-memory dict, not settings, not `entry.options`, not every settings snapshot that gets logged, diagnosed, or sent over the wire); no shared-object exposure (the settings dict is handed around freely, the secret store object never is, its repr prints only key names, values are reachable one key at a time through an explicit await, and no method returns all values at once); and a stronger file mode (`private=True`, 0o600, `atomic_writes=True`, matching core's auth store, so other uids cannot read it where the general file is world-readable). `ALLOWED_SECRET_KEYS` is enforced on every get and set so a future credential cannot drift into the store without first being added to `SECRET_SETTING_KEYS` and therefore to every masking and redaction path.

`async_migrate_legacy_secrets` logs only the count of moved values, never names or values; it `pop()`s rather than `get()`s so no None placeholder is left in settings; the legacy `firewall.addon_secret` key is removed outright; and the old store is rewritten with `async_save_now()`, not on the debounce timer, because until that save lands the plaintext copies are still on disk in the world-readable file.

The general Store is also `private=True, atomic_writes=True`: findings, per-user baselines, and firewall history are sensitive even with the secrets moved out, so the file is written 0o600 via temp file and rename (work item 1.1, D-8 option (a)).

### Fetch at use (SEC-3)

`ws_settings_set` routes secret values to the secret store; they never enter the settings dict. In the audit record every changed key is named but secret values are replaced with the placeholder before the record is built, so no raw secret enters the audit path; `_redact_secrets_deep` stays behind that as defense in depth. `_masked_settings` defensively pops any secret key from the settings copy so a stray value could never reach the wire.

The NVD key is fetched immediately before each HTTP request inside `_async_query_nvd` and dropped with that frame; no parameter, attribute, or global carries it between requests, and `_async_correlate_cves` asks only for presence because pacing depends only on whether a key exists. The GitHub token is fetched per repo inside `_fetch_repo_signals` and dropped; `async_refresh_github_signals` and integration_security.py check presence only. The UniFi keys are fetched into a short-lived `_Conn` whose repr masks the key (the generated dataclass repr would print it into any log line), used for one snapshot, and dropped; nothing long-lived holds a key. Pi-hole's `_Conn` is the same shape, carries the sid in a custom header so it never lands in a proxy access log, and logs out after every snapshot. unifi_core.py copies an explicit whitelist of fields per snapshot instead of copying `.raw` and redacting, so `x_passphrase`, `x_authkey`, serials, tokens, and the rest of the `x_*` family cannot leak into a panel payload; `_snapshot_wlans` copies only id, name, and enabled.

`INTEGRATION_LOCATOR_KEYS` are the only keys HA SOC ever reads out of another integration's config entry (SEC-4). Peripherals matching and Entity ReMap's fallback need to know where a device or entity lives, never its credentials; stringifying whole entries would sweep passwords into a search haystack, the exact pattern the scanner flags elsewhere. `iter_locator_strings` in peripherals.py is the single reading point: nested dicts are descended only under a locator key with the allowlist applied again at every level, non-string scalars are skipped, and nothing read is persisted beyond the entry id, domain, and title. A device path or entity id that appears only inside a stored password does not produce a match, and that is correct.

Diagnostics never include secrets, only whether each is configured; since SEC-1 the values do not pass through the module at all. `_PRIVATE_SETTING_KEYS` (`unifi_network_host`, `unifi_protect_host`) are not credentials but identify the installation, so they are redacted to a presence flag too. The `addon_paired` flag asks the secret store for presence only.

Entity ReMap backups are written 0o600 in a 0o700 directory (re-chmodding a wider existing one), because the previous config of a dashboard or helper is operator data; the `os.sep` strip on the backup stem is defense in depth. The hardcoded-credential scanner rule stores the assignment target plus a masked value (`token = "[redacted, 40 chars]"`), because if the match is real the literal is a live credential that would otherwise travel into the store, every WebSocket listing, and the GHSA export text (work plan item 1.3). The GHSA export is copy-to-clipboard only, never a submission channel; the confirmation names the stored snippet and the target integration because the copied text is the one thing in the view designed to leave the instance.

### Data disclosure

The CVE correlation pass sends device manufacturer and model strings from the device registry to NIST's NVD over HTTPS, together with the optional API key. Nothing else leaves the instance. The pass is on by default, disclosed in the Settings tab, and switched off by `nvd_lookups_enabled` (D-12, work plan item 4.9).

## Redaction rules

Redaction runs inside `AuditLog.async_log` itself, one chokepoint every record passes through, never per call site, so no path can forget it. Every detail payload passes through `_redact_service_data` (credential-shaped keys, deep) and `_redact_secrets_deep` (HA SOC's own secret setting keys). `_handle_call_service` performs no redaction of its own (work item 1.6).

- A key in `_REDACTED_SERVICE_DATA_KEYS` (`password`, `token`, `code`, `api_key`, `apikey`, `secret`, `pin`, `passphrase`, `access_token`, `refresh_token`, `client_secret`, `authorization`, `probe_secret`) is masked wherever it appears, any depth, inside lists too, matched case-insensitively on the exact key name; substring matching would eat harmless keys like `token_id` that the panel displays.
- `message` and `title` are masked for the `notify`, `tts`, and `persistent_notification` domains, and only for service-call records: a config-entry record for the same domain carries a title that is the entry's display name. What a notification said is personal, not operational; only that one was sent is recorded.
- `payload` is masked for `mqtt.publish`, because an MQTT payload carries whatever the automation put in it.
- Values are replaced unconditionally, even empty ones, so the log never reveals whether a field was filled in.
- `probe_secret` is in the list because the pairing secret rides in the `service_data` of every Probe service call, which the `call_service` event delivers straight into audit.py; without it the chain would archive the credential on every poll.
- `_redact_secrets_deep` masks any value under a `SECRET_SETTING_KEYS` key, however deeply nested (settings changes log under `detail["changes"][<key>]`), so `nvd_api_key` or `github_token` can never reach the append-only files verbatim. This is the shared enforcement point the red-team review asked for.

`SECRET_SETTING_KEYS` values are never logged verbatim and never returned raw to the frontend; every future credential-shaped setting must be added there. `REDACTED_PLACEHOLDER` is the literal "[redacted]".

## Audit chain integrity

The chain is tamper evidence, not tamper proofing. `async_verify_chain` proves the on-disk chain is internally consistent from the retention anchor forward: every surviving record's hash matches `prev_hash` plus its content, starting from the anchor when old day files expired or from the first record when nothing has. It cannot prove the files were never touched: anything with the same filesystem access (an SSH or Terminal add-on, Samba, the File Editor add-on, root on the host) can rewrite `chain_head.json`, the anchor, and every hash to match. Real integrity guarantees require exporting the chain off the box as it is written; the 0o600/0o700 modes match core's auth store but cannot protect against a same-uid attacker.

Verification reads the anchor, reset marker, and checkpoint from disk rather than memory, because it must judge what an attacker could have edited. The walk starts from whichever discontinuity is further along: the retention anchor (records legitimately expired) or the reset marker (records lost to a wipe). Both carry the seq and hash the surviving chain continues from; an anchored start can end in `ok`, a reset start never can while the marker exists. `last_seq` begins at the start point so expiry, possibly of every file, is not read as truncation. No surviving record may sit at or before the start point: the anchor asserts everything through its seq expired and the reset marker asserts everything through its seq was lost, so such a record is resurrected data or a forged marker. The first surviving record must be the start point's direct successor. A contradiction is reported under the contradicted marker's name (`anchor_inconsistent` or `chain_reset`).

Completeness, not just consistency: the walk can reach a clean end even if the newest records were deleted, because nothing on disk points forward to an unwritten record. The last record seen is cross-checked against the separately stored checkpoint; if the checkpoint is ahead, the tail was truncated since the last flush, the cheapest way to hide one's own recent actions (`tail_truncated`). This still cannot catch an attacker who rewrites both the log and `chain_head.json` (that needs an off-box anchor), but it closes the plain-truncation gap. A malformed anchor reads as absent, so verification starts at genesis and fails loudly if records really expired; a malformed reset marker likewise reads as absent and fails at the walk.

Wipe and rollback detection: after every successful flush the head is mirrored into the general store (`audit_head`), a separate file an attacker would have to falsify consistently. Only a successful flush advances the mirror. At startup an on-disk head that is absent or behind the mirror means the directory was wiped, replaced, or rolled back. The response is threefold: an `audit_chain_reset` record carrying both heads is written as the first record of the continued chain with the mirror's hash as its `prev_hash`, numbered `mirror_seq + 1`, so the discontinuity is itself chained; a Repairs issue is raised so a human sees it; and `chain_head.json` keeps a persistent reset marker. An on-disk head ahead of the mirror is normal: the mirror's save is debounced, so a crash can lose its last update while the head was written synchronously. While the marker exists, `async_verify_chain` reports `chain_reset` both when the store mirror is ahead of the on-disk head (wiped and not yet restarted) and while the head file carries the marker; the continued chain is still re-verified record by record, but `ok` would falsely claim an unbroken history, so until the marker ages out the honest answer is "reset, then clean" (work item 1.5). The Repairs issue is ERROR, not CRITICAL, because the chain has been continued and new records are being written; it means "evidence was destroyed and you must know", it is not fixable because nothing restores deleted records, and the operator's action is to investigate who could reach `.storage/`.

File modes: the directory is 0o700 and every file in it is opened through `os.open` with 0o600, so no other uid can read the log; `makedirs`' mode is subject to umask and ignored for an existing directory, so the explicit chmod is what guarantees 0o700, and a plain `open()` would create files at the umask's 0o644. Files a pre-1.1 build left wider are tightened once at startup (work item 1.1).

## Boundary-widening checks

health.py watches for configuration that widens who can read HA SOC's private files or blinds its own capture (SEC-7, plus work item 1.7's ban-logger check): on-disk modes of `secrets.yaml` and `.storage`, add-ons known to map the config directory, backups stored without protection, a Samba share without authentication, and the `http.ban` logger being silenced. Every value those checks read is a file mode, a boolean, or an option key name, never a secret value; 0o077 masks exactly the group and other bits that let another uid reach a file, and the `# ha-soc-allow: storage_file_access` markers on those checks state exactly what is read. With X-Forwarded-For trusted from too many hosts, any of them can spoof a client IP and bans, trusted_networks, and every IP-based detection judge the wrong address, so a `trusted_proxies` network broader than /24 or /64 is flagged (work plan item 4.2). Trusted-networks mappings to an admin, the owner, or the admin group grant passwordless, MFA-free privileged login to anyone on that network. `_path_exists` in config_hygiene is `isfile()` only inside the www directory, with both sides realpath'd first, because a resource URL is attacker-influenceable and `/local/../../secrets.yaml` would otherwise be stat'd outside www. `_SERVICE_REF_OPAQUE_KEYS` (`data`, `data_template`, `variables`) are payload subtrees, so an `action:` key inside a notify payload is never treated as a service reference (work plan item 4.6). The add-on slug in an `addon:<slug>` log target is interpolated into a Supervisor URL, so only a slug the Supervisor reports installed is accepted. `safeHref` in the Network view is a client-side scheme gate for every external href: camera and thumbnail links are built from controller-supplied host strings, so a hostile controller could hand back a `javascript:` or `data:` URL; only http(s) reaches an anchor, and a value not parseable as an absolute URL is refused (work plan item 4.12).

## Detection false positives

Each rule's dominant false-positive shape, so an analyst knows how to sanity-check the alert:

- `brute_force_ip`: a household's shared NAT or a busy guest network racks up failed logins from unrelated people, not one attacker.
- `success_after_failures`: the owner mistypes their password a few times, then logs in fine; `require_new_token` removes the noisiest sub-case, a background refresh that shared an IP with someone else's failures (D-9, work item 3.8).
- `new_ip_login`: carrier CGNAT or a VPN hands out a different prefix every session; such a user is flagged for the first `baseline_days_required` days on each prefix, the recorded secure-default trade, because amnesty would also cover an attacker's first login (D-9). Private and unparseable IPs are excluded, an unparseable address counting as private so garbage is never flagged.
- `off_hours_anomaly`: the owner is travelling or cannot sleep and genuinely operates the house at 3 am.
- `dormant_revival`: a seasonal resident disappears for months.
- `privilege_escalation`: none by design; a legitimate promotion looks identical to an attacker granting themselves admin, so the rule is an audit-trail entry, not proof of compromise.
- `mass_entity_burst`: a human tapping through many tiles by hand.
- `token_minting_anomaly`: setting up several devices in one sitting.
- `disabled_user_activity`: a forgotten wall tablet or old script retrying against a deactivated account.
- `probe_auth_rejected`: an outdated Probe build predating `probe_secret` is rejected with `no_secret` until updated; noisy but honest, since Core cannot tell it from a forger.
- Security Integrations Health's no-state row: an integration still starting up shows its entities as problems for the first moments after a restart (work plan item 4.5).

## Scanner rules: false positives and evasion

Every rule matches unobfuscated instances only: string-built calls, computed names, and encoded literals are invisible by design, and the Scanner tab says so (work plan item 4.8). Rules 7 through 10 only see what is statically visible in one file's AST; `THREAT-MODEL.md`'s "Cross-integration extraction rules" note holds the design rationale, and HA SOC's own code must pass all four with zero open findings without any special-casing of the `ha_soc` domain.

- Rule 2, `shell_injection_risk`: `shell=True` alone is not the signal, since a literal command is not attacker-controlled; the rule fires only alongside an argument built from an f-string, concatenation or %-format, or `.format()`. `os.system` and `os.popen` always hand their argument to a shell, so the interpolation co-condition alone triggers. False negative: a command assembled into a variable before the call.
- Rule 4, `insecure_deserialization`: `yaml.safe_load` never reaches the rule because its name is not `load`.
- Rule 5, `hardcoded_credential`: a name-pattern plus literal-string heuristic with no entropy check, so fixtures, docs examples, and test constants match too, an accepted permanent source of false positives; confidence stays medium forever by design. Two guards: `CONF_*` constants hold a config-schema key name, never a secret, and are excluded by name; an ALL_CAPS constant ending in `_KEY` or `_KEYS` (optionally `_NAME`) whose literal is a multi-word, digit-free lowercase identifier names a storage key (`PROBE_PAIRING_SECRET_KEY = "probe_pairing_secret"` is the shape). `API_KEY = "hunter2secret9"` still fires on its digits. Documented false negative: a digit-free, multi-word, lowercase credential assigned to an ALL_CAPS `*_KEY` name.
- Rule 7 (SEC-5 a), `foreign_config_entry_read`: a `config_entries.async_entries()` or `async_loaded_entries()` call qualifies when it passes no domain (indiscriminate) or a literal domain different from the scanned one (targeted). It fires only when, in the enclosing scope, a variable bound to the entries has its `.data` or `.options` consumed wholesale (f-string, `str()`/`dict()`/`json.dumps()`, logging, iteration, assignment onward beyond one recognized alias), or via a literal key outside `INTEGRATION_LOCATOR_KEYS` for an indiscriminate call, or a credential-shaped key for a targeted call; targeted enumeration fires only on credential-shaped keys because a visible read of one named domain's non-secret fields is how legitimate cross-integration features are built. Exempt: subscript or `.get` with a passing key, membership tests, and passing the mapping to a callable outside the consuming set (`str`, `repr`, `format`, `dict`, `list`, `tuple`, `set`, `sorted`, `iter`, `dumps`, `dump`, `pformat`, logger methods), whose effect is statically unknowable. Bare enumeration for `entry.domain` or `entry.state`, a variable domain, or a non-literal key never fires. False positive: a function that enumerates for domains and legitimately reads a non-locator field of a cooperating entry. Evasion: a domain or key held in a variable, or the mapping passed to a helper in another scope.
- Rule 8 (SEC-5 b), `storage_file_access`: only file-touching calls are inspected (`open`, `Path(...)`, `.read_text`/`.read_bytes`/`.write_text`/`.write_bytes`/`.open`, `os.path.join`, `hass.config.path`). Any literal containing `secrets.yaml` fires unconditionally, since no integration owns a namespace inside it. A literal whose path component is exactly `.storage` fires only when the following component (same literal or next literal argument) is visible and does not start with the scanned domain. False positive: a filename merely containing `secrets.yaml` (`my_secrets.yaml`), or a documented backup or migration helper. Evasion: a path assembled from variables, constants, or f-strings, or a file API outside the inspected set.
- Rule 9 (SEC-5 c), `foreign_hass_data_read`: fires on a subscript of an attribute named `data` whose base ends in `hass` or `_hass`, with a literal key that is a valid domain, is not the scanned domain or a key prefixed with it, and is not a core bootstrap HassKey name in `_CORE_HASS_DATA_KEYS`. A custom domain colliding with one of those names is a documented false negative. Reads and writes both fire. False positive: reading a core component's published slot, or a documented cooperating family. Evasion: a key in a variable or constant (the way most code spells `hass.data[DOMAIN]`), an f-string key, or `.get()`.
- Rule 10 (SEC-5 d), `foreign_storage_key`: fires on calls whose callee is `Store` (bare, dotted, or `Store[...]`) where the key (third positional or `key` keyword) is a literal whose first dotted component is not the scanned domain; `Store(hass, 1, "core.config_entries")` outside core opens another party's private file through the helper that owns its format. False positive: a documented shared namespace, or a brand-prefixed key predating the current domain. Evasion: a `Store` subclass under another name, or a key in a variable, constant, or f-string.
- `_is_own_namespace` treats a name as inside the scanned namespace when it equals the domain or is the domain followed by `.`, `_`, or `-`.
- Acknowledgment: `# ha-soc-allow: <pattern_id> <reason>` on the flagged line or the line above marks a finding acknowledged; it is still produced and stored (never a silent skip) but opens no Repairs issue. It is honored only for the four extraction rules, must name the exact pattern id, and must carry a non-empty reason. It is text-based on purpose so it is greppable where the code is; a comment-shaped string literal on the same line would also satisfy it, acceptable for an advisory mechanism.

Slug hardening for provenance lookups (work plan item 4.10, GH-1): the `owner/repo` slug comes from a third-party manifest's URLs, and yarl normalizes `..` path segments before sending, so an unvalidated slug like `../../user/repos` would redirect the owner's token to an arbitrary API path and cache the response. Every slug is validated against `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$` with `.` and `..` components rejected outright; the endpoint is a hardcoded constant and the token is a header, never spliced into a URL. A 403 with `X-RateLimit-Remaining: 0` stops the whole refresh so a big install does not burn its quota discovering the limit one repo at a time.

UniFi and Pi-hole client hardening (work plan item 4.11): redirects are never followed (aiohttp strips only Authorization-family headers on cross-origin redirects, not custom ones like `X-API-KEY`), bodies are capped by both declared Content-Length and actual read (8 MB UniFi, 4 MiB Pi-hole), the whole Network overview runs under a 60 s wall-clock budget, pagination is bounded, and `_validate_host` rejects anything beyond a scheme, address, and port, since userinfo in the authority is a classic way to disguise the real target while the key rides along; an invalid host is shown as a configuration error, not "not configured". `_hosts_from_value` never raises on another integration's garbage host field. `_fetch_broadcast_map` and `_fetch_network_map` swallow only `UniFiError` so a programming error surfaces loudly.

Integration Security is a provenance score, never a safety score; no surface may say Safe, Verified, or Trusted.
